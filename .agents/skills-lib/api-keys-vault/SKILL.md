# API KEYS VAULT — навык хранителя ключей

## Золотое правило

**Любой ключ/пароль/доступ, встреченный в работе → в `D:\Downloads\API_KEYS`.**
**Но сначала — проверка на дубликат.** Если ключ уже лежит в хранилище, НЕ перезаписывать и не создавать вторую папку.

## Структура хранилища

```
D:\Downloads\API_KEYS\
├── README.md                  — карта всех сервисов (обновлять при добавлении)
├── SSH_КЛЮЧИ_РЕЕСТР.md        — реестр SSH-ключей: сервер, адрес, отпечатки
├── <Имя сервиса>/             — ОДНА папка = ОДИН сервис/аккаунт
│   ├── API_KEY.txt            — сам ключ/пароль
│   ├── INFO.md                — что за сервис, endpoints, статус проверки, риски
│   └── (для SSH: файлы ключа с исходными именами + .ppk-вариант для WinSCP)
```

Существующие папки-примеры: `DeepSeek/`, `Gmail - <адрес>/`, `Hetzner AX41 (SSH)/`, `Hetzner ufc333 (SSH)/`, `Google Cloud (SSH)/`, `Traveldesk/`.

## Процедура при разговоре о ключе

1. **Понять тип:** API-ключ, пароль приложения, SSH-ключ, токен, куки, файл доступа.
2. **Сначала искать в хранилище:** `ls "D:\Downloads\API_KEYS"` → грепнуть по имени сервиса/аккаунта. Если ключ УЖЕ там — сказать владельцу где лежит, не дублировать.
3. **Если новый:**
   - API-ключ/пароль → `API_KEYS\<Сервис>\API_KEY.txt` + `INFO.md` (сервис, дата добавления, статус).
   - SSH-ключ → `API_KEYS\<Сервер> (SSH)\<имя_файла>` (+ `.pub` и `.ppk` если есть). В `INFO.md` — адрес, пользователь, как подключаться.
   - Обновить `README.md` (строка в карте) и `SSH_КЛЮЧИ_РЕЕСТР.md` (для SSH).
4. **Если ключ сменился/устарел:** старый файл НЕ удалять — переименовать в `<имя>_superseded_YYYY-MM-DD` или пометить `archived` в INFO.md. Новый рядом.
5. **Никогда:**
   - не удалять ключи из хранилища (глобальное правило владельца 2026-09-12);
   - не коммитить в git, не лить в облако;
   - не печатать содержимое приватных ключей в чат/логи/файлы-отчёты;
   - не просить владельца ротировать/удалять доступы.
