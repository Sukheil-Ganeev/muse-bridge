# EXP-058: Миграция CRM с vanilla JS на Next.js + PostgreSQL за одну сессию

**Дата:** 2026-02-27
**Тип:** pattern
**Severity:** high
**Контекст:** Tourism CRM v3.0 (vanilla JS + localStorage, 11K строк) -> v4.0 (Next.js 15 + Prisma v7 + PostgreSQL)
**times_applied:** 1

## Урок

Полная миграция legacy SPA на modern stack возможна за одну сессию при правильной стратегии:

### Стратегия "Новый скелет, старые мозги"
1. **НЕ копировать код** -- архитектуры несовместимы (innerHTML vs React, localStorage vs PostgreSQL)
2. **Извлечь бизнес-логику** -- модели данных, формулы, enum-значения, переводы
3. **Строить модулями** -- каждый модуль = вертикальный срез (API + типы + компоненты + страницы)
4. **Параллелить независимые модули** -- Products, Suppliers, Customers одновременно (x3 ускорение)

### 10-этапная декомпозиция (работает)
```
Этап 1: Каркас + БД          <- фундамент, всё зависит от него
Этап 2: Авторизация           <- зависит от 1
Этап 3: Layout                <- зависит от 2
Этап 4: UI Kit                <- зависит от 1 (параллельно с 2-3!)
Этап 5-7: Модули (параллель)  <- зависят от 3+4
Этап 8: Orders                <- зависит от 5+6+7
Этап 9-10: Dashboard + i18n   <- параллельно
```

### Критические моменты
- **Prisma v7** имеет breaking changes: adapter pattern, prisma.config.ts вместо url в schema
- **FilterValues type** -- если компонент FilterBar экспортирует свой тип, не создавай локальный с дополнительными полями -- используй index signature `[key: string]: string`
- **Soft delete** -- добавляй `deletedAt` и фильтруй ВЕЗДЕ, иначе удалённые записи будут появляться
- **AGENT изоляция** -- проверяй на КАЖДОМ endpoint (не полагайся только на middleware)
- **Decimal -> Number** -- Prisma Decimal не сериализуется в JSON, нужно `Number(field)` в каждом API response

### Результат
- ~85 файлов за одну сессию
- 11 таблиц PostgreSQL с 30+ индексами
- 19 маршрутов (static + dynamic)
- 7 бизнес-модулей с полным CRUD
- 3 языка (RU/EN/AR) + RTL
- JWT RBAC (3 роли)
- 0 TypeScript ошибок в финальной сборке

## Применение
- При любой миграции legacy -> modern: сначала извлечь данные, потом строить новое
- Параллелить независимые модули через субагентов
- Всегда начинать с БД schema + seed (остальное строится поверх)
- FilterBar/DataTable -- делать максимально generic (index signature типы)
