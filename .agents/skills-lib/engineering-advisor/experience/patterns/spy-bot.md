# EXP-EA-SB001: Spy-Bot Refactoring (2026-02-18)

**Проект:** Рефакторинг Telegram spy-bot (aiogram 2->3, sync->async, GPT->Gemini)
**Масштаб:** 30+ файлов создано, 98 тестов, 5 волн, 5 параллельных агентов
**Триггеры:** #1, #2, #3, #4(MANDATORY), #5, #6, #7, #9, #10 — ВСЕ 10 одновременно

## Уникальность проекта

Первый случай когда **ВСЕ 10 триггеров** engineering-advisor сработали одновременно в одном проекте.
Это максимальная валидация системы триггеров — каждый из них нашёл реальную проблему.

## Волны реализации

| Волна | Содержание | Ключевой принцип |
|-------|-----------|-----------------|
| Wave 0 | Security: удаление хардкод-токенов | MANDATORY #4 — безопасность ПЕРВАЯ |
| Wave 1 | Core: config, database, models | Фундамент для всего остального |
| Wave 2 | Logic: handlers, services (5 агентов) | Параллелизация по файлам |
| Wave 3 | Wiring: imports, __init__.py, run.py | 48 tool uses для фиксов импортов |
| Wave 4 | Tests: 98 тестов | Доказательство вместо слов (#7) |

## Ключевые уроки

### 1. MANDATORY #4 работает — безопасность ПЕРВАЯ
Хардкод-токены были во 2 файлах (config_old.py + listener.py).
Wave 0 security = 55 сек выполнения, но предотвращает утечку токенов во все последующие волны.
Без Wave 0: токены попали бы в новые файлы через copy-paste из старого кода.

**Вывод:** Wave 0 Security должен быть СТАНДАРТОМ для любого рефакторинга legacy-проекта.

### 2. Тесты = лучшее доказательство (#7)
"Готово" подтверждено 98 тестами, а не словами.
`pytest` с реальным запуском > "должно работать".
Без тестов невозможно проверить что миграция aiogram 2->3 не сломала бизнес-логику.

**Вывод:** Для миграций (#9) тесты ОБЯЗАТЕЛЬНЫ, не Advisory.

### 3. Детальный план окупается 10x (#9, #10)
Детальный план из 5 волн + 13 агентов дал:
- 0 retry (каждый агент знал свои файлы)
- 0 конфликтов файлов (разделение по файлам, не по функциям)
- 0 потери работы (каждая волна проверена перед следующей)

Без плана: хаотичные правки, конфликты, потеря работы, бесконечные итерации.

**Вывод:** Для миграций план = обязательный артефакт, не опциональный.

### 4. Compound Engineering в действии
Каждая волна строилась на проверенной предыдущей:
```
Wave 0 (security) → check
Wave 1 (core) → Gate 1 (imports work?)
Wave 2 (logic) → Gate 2 (services work?)
Wave 3 (wiring) → Gate 3 (bot starts?)
Wave 4 (tests) → 98/98 pass
```
Ошибка в Wave 1 была бы обнаружена в Gate 1, а не в Wave 4.
Wiring-агент (Wave 3) сделал 48 tool uses — это нормально, потому что он чинит связи а не бизнес-логику.

### 5. Миграция (#9) требует отдельной волны на wiring
aiogram 2->3 + sync->async + GPT->Gemini = три миграции одновременно.
Wave 3 (wiring) был самым трудоёмким: 48 tool uses на фиксы импортов.
Это подтверждает PAT-004: wiring = отдельный этап ПОСЛЕ параллельных агентов.

### 6. Wiring-агент = отладчик, не разработчик
48 tool uses wiring-агента — это не баг процесса.
Это НОРМАЛЬНАЯ цена интеграции 30+ файлов от 5 разных агентов.
Без отдельного wiring-этапа: каждый агент пытается чинить чужие импорты = конфликты.

## Анти-паттерны (что НЕ делать)

- НЕ начинать рефакторинг без проверки хардкод-секретов
- НЕ делать миграцию без тестов — невозможно проверить что ничего не сломалось
- НЕ совмещать wiring с написанием бизнес-логики — разные навыки, разные агенты
- НЕ пропускать Wave 0 Security "потому что это внутренний проект" — привычка важнее контекста
