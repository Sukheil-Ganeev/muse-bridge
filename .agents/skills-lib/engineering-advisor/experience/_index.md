## Критические уроки (Топ-5)

### EXP-053: aiogram 3 — порядок хэндлеров = приоритет команд (CRITICAL)
**Контекст:** VoiceTranscriptionBot v5.4.0 — `/calc`, `/rate`, `/route` молча не работали. 67/67 тестов зелёные.
**Урок:** В aiogram 3.x `@router.message(F.text)` catch-all, объявленный ВЫШЕ `Command("calc")`, перехватывает ВСЕ текстовые сообщения включая команды. `return` внутри catch-all = сообщение обработано, Command-хэндлер никогда не вызывается.
**Применение:** ВСЕГДА размещай `Command()` хэндлеры ВЫШЕ `F.text` catch-all. Мнемоника: «Конкретные фильтры — вверху, общие — внизу. Как воронка.»

### EXP-040: ВСЕГДА сверяй имена полей с @dataclass определением
**Контекст:** VoiceTranscriptionBot v4.5.0 — `result.text` использовался в 6 местах, но в PipelineResult поле называется `result.transcription`
**Урок:** ВСЕГДА сверяй имена полей с @dataclass определением. `result.text` != `result.transcription`. 6 багов в одном файле из-за одной опечатки в имени атрибута.
**Применение:** Перед использованием dataclass/NamedTuple — открыть определение и проверить точные имена полей. Grep по проекту на каждое обращение к атрибуту.

### EXP-041: MagicMock() без spec= скрывает баги
**Контекст:** VoiceTranscriptionBot — все pipeline тесты использовали MagicMock() без spec, скрывая AttributeError
**Урок:** MagicMock() без spec= скрывает баги. Тесты зелёные, прод падает. ОБЯЗАТЕЛЬНО: `MagicMock(spec=RealClass)`.
**Применение:** В каждом тесте где мокируется объект — добавлять spec=. Без spec MagicMock возвращает новый MagicMock на ЛЮБОЙ атрибут, включая несуществующие.

### EXP-065: Singleton + attribute rename + MagicMock без spec = silent production failure (CRITICAL)
**Контекст:** Spy Bot v4 — переименовали `_gemini_model` → `_gemini_client` в AIClient (Singleton). Тесты с MagicMock() без spec продолжали обращаться к `_gemini_model` — mock молча создавал несуществующий атрибут. Тесты зелёные, прод — AttributeError.
**Урок:** EXP-040 + EXP-041 в комбинации с Singleton = максимально опасный баг. Mock скрывает rename, Singleton шарит один инстанс. После ЛЮБОГО attribute rename → `grep -r "old_name" .` по ВСЕМУ проекту (включая тесты). `MagicMock(spec=RealClass)` ловит это автоматически.
**Применение:** Чек-лист после rename: (1) grep, (2) fix all refs, (3) verify spec= in mocks, (4) singleton reset in teardown.

### EXP-073: Caller-callee signature drift after DB method refactoring (CRITICAL)
**Контекст:** VIP-DXB-CatalogBot — после рефакторинга `get_bestsellers()` и `get_card_cross_sell()` callers продолжали использовать старые сигнатуры. Unit-тесты с mock зелёные, runtime crash.
**Урок:** После ЛЮБОГО изменения сигнатуры метода — обязательный `grep -rn "method_name" --include="*.py" .` по ВСЕМ callers. Mock-based тесты НЕ ловят signature drift — mock принимает любые аргументы. Нужен хотя бы 1 integration test с реальным объектом.
**Применение:** Чек-лист: (1) grep all callers, (2) update call sites, (3) update mock specs, (4) add integration test. Мнемоника: «Refactor method = grep callers».

### EXP-061..063 (PAT-031): Трёхфазный AI-рефакторинг v6.1.0 (2026-02-28)
**Контекст:** VoiceTranscriptionBot v6.1.0 — миграция deprecated Gemini моделей + консолидация LLM клиентов + TaskType routing. 15+ файлов, 2138 тестов.
**Урок:** Крупный рефакторинг делить на 3 фазы: A (quick wins: 8 строк model ID) -> B (architecture: 5 модулей на DI) -> C (optimization: TaskType enum). Pytest между каждой фазой. Никогда не создавать `genai.Client()` в бизнес-логике — только через DI singleton. CLASSIFICATION задачи (sentiment, categories) работают на дешёвой модели без потери качества = 3x экономия.
**Применение:** Любой рефакторинг 10+ файлов: разделяй по уровню риска, тестируй между фазами. Централизуй model ID как константы.

### EXP-046 (PAT-023): Formatting refactoring -- 0 тестов сломано при 12 файлах (2026-02-21)
**Контекст:** ContentFactory Волна 7 — рефакторинг форматирования 12 хэндлеров Telegram-бота. formatter.py с 18 хелперами. XSS закрыты в 4 файлах.

### EXP-006 (FIX-001): Синхронизируй числовые пороги между YAML и телом
**Контекст:** Полировка скилла — порог 30 в YAML, 50 в тексте
**Урок:** Все числовые пороги должны быть одинаковы в trigger-секции и в теле документа. Два числа для одного понятия = гарантированное рассогласование при обновлении.
**Применение:** Унифицировано к > 50 строк. При создании скиллов — одно число, одно место определения.

### EXP-007 (FIX-002): Триггеры = глагол + контекст, не просто глагол
**Контекст:** Широкие триггеры ("сделай", "напиши") ложно активировались на нетехнических запросах
**Урок:** Изолированные глаголы совпадают с 70% запросов. Добавление контекстного квалификатора ("В КОНТЕКСТЕ КОДА") снижает false positive без потери true positive.
**Применение:** Формат триггера: `глагол — В КОНТЕКСТЕ X (список объектов)`.

### EXP-008 (IMP-001): Каждая делегация = карточка в матрице обнаружения
**Контекст:** superpowers:brainstorming была в таблице делегации, но без карточки действия
**Урок:** Делегация без карточки = невидимый маршрут. Пользователь не попадёт на дорогу, которой нет на карте. Секция 3 и секция 8 должны быть синхронны.
**Применение:** Добавлена секция 3.9 + строка в cheatsheet + строка в reference card.

### EXP-009 (IMP-002): Шпаргалка — зеркало матрицы обнаружения
**Контекст:** 9 паттернов в SKILL.md, но только 9 промптов в cheatsheet (не хватало "петли ошибок")
**Урок:** Пользователь ищет промпты в двух местах: SKILL.md и cheatsheet.md. Оба должны давать одинаковый ответ. Перекрёстные ссылки между FAQ и шпаргалкой помогают навигации.
**Применение:** Добавлен 10-й промпт + 2 строки в таблицу + ссылки из FAQ.

### EXP-010 (PAT-001): Исключения ВСЕГДА важнее позитивных триггеров
**Контекст:** Запрос попадал одновременно в триггер И в исключение — поведение было неопределено
**Урок:** Принцип "deny overrides allow". Лучше одна ложная деактивация, чем одна ложная активация. Пользователь может вызвать скилл вручную, но не может выключить навязчивый скилл.
**Применение:** Явное правило приоритета добавлено в YAML frontmatter.

### EXP-011 (WARN-001): НЕ используй catch-all триггеры
**Контекст:** Триггер "Любая работа с кодом" превращал скилл в спам-бота
**Урок:** Catch-all триггеры активируются на ВСЁМ, превращая советника в назойливый попап. Узкие триггеры пропускают 10% релевантных запросов, но не раздражают на 30% нерелевантных.
**Применение:** Удалён catch-all. Триггеры сужены до конкретных глаголов + контекст.

### EXP-012 (FIX-003): Широкие исключения блокировали 90% срабатываний
**Контекст:** Триггеры почти никогда не срабатывали — исключения ("текстовые задачи", "WhatsApp", "документы") покрывали почти все запросы пользователя
**Урок:** Исключения должны быть ТОЧНЫМИ (конкретные расширения файлов, а не категории деятельности), а приоритет — условным (проверка наличия файла кода), а не безусловным блоком. Правило "deny overrides allow" работает только когда deny-список узкий.
**Применение:** Исключения сужены (7 → 6), добавлен условный приоритет: если есть файл .py/.js/.ts — активировать даже при наличии исключения. Триггеры расширены (8 → 9, добавлен деплой).

### EXP-013 (PAT-002): Compound Engineering + Verification-before-completion
**Контекст:** ContentFactory — Telegram-бот, 41 файл, 133 теста, 6 волн реализации
**Урок:** Если детальный дизайн-документ существует, триггер #10 (3+ файлов) можно понизить до Advisory. Compound Engineering (plan -> work -> verify -> extract lessons) через 6 волн даёт значительно выше качество кода чем "написать всё за раз". Verification-before-completion (реальный запуск) ловит баги которые тесты пропускают (TypeError в конструкторах).
**Применение:** При наличии дизайн-документа — не блокировать на триггере #10. Всегда запускать проект после "готово". Compound цикл = каждая волна строится на проверенном фундаменте предыдущей.

### EXP-014 (PAT-003): Тесты = достаточная верификация для кодовых проектов
**Контекст:** ContentFactory Волна 3 — 56 файлов, 338 тестов, тест-агент запускает pytest
**Урок:** Триггер #7 (верификация) для кодовых проектов с хорошим покрытием тестами: отдельный verification step не нужен, pytest IS the verification. 338 тестов, все passing — это и есть "фактический результат". Отдельный ручной запуск имеет смысл только при первом деплое или при отсутствии тестов.
**Применение:** Если проект имеет >100 тестов с хорошим покрытием — триггер #7 удовлетворяется прохождением тестов. Не требовать дополнительного ручного запуска.

### EXP-015 (PAT-004): Параллельные агенты без конфликтов = правило "свои файлы"
**Контекст:** ContentFactory 3 волны — до 7 параллельных агентов, 0 конфликтов
**Урок:** Триггер #6 (3+ параллельных задач) масштабируется до 7 агентов при одном правиле: каждый агент создаёт ТОЛЬКО свои файлы, никогда не редактирует чужие. Wiring (связывание модулей, __init__.py, imports) выполняется ОТДЕЛЬНЫМ шагом после завершения всех агентов.
**Применение:** При параллелизации — разделять по файлам, не по функциям. Wiring = отдельный этап. 0 конфликтов за 3 волны подтверждает паттерн.

### EXP-016 (PAT-005): План из файла заменяет EnterPlanMode
**Контекст:** ContentFactory Волны 2-3 — ПРОДОЛЖЕНИЕ_ВОЛНА_N.md
**Урок:** Триггер #10 (фича 3+ файлов) не требует формального EnterPlanMode если план уже записан в файл (ПРОДОЛЖЕНИЕ_ВОЛНА_N.md). Этот паттерн работает лучше: план написан до начала волны с полной рефлексией, агенты получают конкретные задачи с именами файлов.
**Применение:** Для многоволновых проектов — план каждой волны в отдельном .md файле. Триггер #10 удовлетворяется наличием файла-плана.

### EXP-017 (PAT-006): Graceful degradation для API ключей
**Контекст:** ContentFactory — 56 файлов, все ENV через config.py, ни одного хардкода
**Урок:** Триггер #4 (безопасность) удовлетворяется паттерном: config.py читает os.environ, каждый модуль проверяет наличие ключа и деградирует gracefully (AI adapter возвращает оригинальный текст, интеграции отключаются, бот продолжает работать).
**Применение:** Рекомендовать паттерн: единый config.py + graceful degradation. Не просто "убери ключ из кода", а "убери и покажи что будет без ключа".

### EXP-018 (PAT-007): Бизнес-формулы ОБЯЗАТЕЛЬНО покрывать тестами
**Контекст:** ContentFactory Волна 3 — MetricsService, ScoringService, ABTestService
**Урок:** Триггер #3 (бизнес-логика) подтверждён на формулах: engagement_rate = (likes+comments+shares)/views*100, weighted average 5 критериев, confidence formula для AB-тестов. Каждая формула имеет dedicated тест. Ошибка в формуле engagement = потеря доверия к аналитике.
**Применение:** Любая числовая формула в бизнес-логике — Recommended уровень для тестирования. Один тест на формулу = минимум.

### EXP-019 (PAT-008): Compound Engineering через субагентов — встроенная верификация
**Контекст:** ContentFactory 3 волны — каждый субагент: Read -> Write -> Read (верификация)
**Урок:** Compound Engineering цикл работает не только на уровне волн, но и на уровне каждого субагента. Каждый агент: читает задание, пишет код, перечитывает написанное (Read после Write). Verification встроена в workflow каждого агента, а финальный pytest подтверждает интеграцию. Двойной слой верификации: per-agent + per-wave.
**Применение:** При делегации субагентам — требовать Read после Write. Финальный pytest = интеграционная верификация.

### EXP-020 (PAT-009): SingaporeToursBot — Архитектурные решения

**Контекст:** Telegram-бот для туризма в Сингапуре. aiogram 3.x + SQLite/FTS5 + Gemini/Groq + python-dotenv. 32+ файлов, 11 таблиц, 68 ключей i18n x 3 языка. Создано за 1 сессию с 4 параллельными агентами.
**Урок:** Набор архитектурных решений подтверждённых на 3-м проекте: модульные handlers (Router per feature), Database DI через dp["db"], FTS5 для мультиязычного поиска, JSON i18n с t(key,lang), Navigation Stack in-memory, Dual Backend AI (Gemini->Groq), 3-уровневая комиссия с fallback-цепочкой, реферальные deeplinks с UNIQUE constraint.
**Применение:** Эти паттерны переиспользуемы в любом Telegram-боте с каталогом, мультиязычностью и партнёрской программой.

### EXP-021 (PAT-010): Wave 0 Security = стандарт для рефакторинга legacy
**Контекст:** Spy-Bot refactoring — хардкод-токены в 2 файлах (config_old.py, listener.py). ВСЕ 10 триггеров EA сработали одновременно.
**Урок:** При рефакторинге legacy-проекта ПЕРВАЯ волна = удаление хардкод-секретов. 55 секунд работы предотвращают утечку токенов во все последующие волны (copy-paste из старого кода). MANDATORY #4 подтверждён на практике — без Wave 0 токены попали бы в 30+ новых файлов.
**Применение:** Wave 0 Security = обязательный шаг для любого рефакторинга. Чек-лист: grep по старому коду на API_KEY, TOKEN, SECRET, PASSWORD.

### EXP-022 (PAT-011): Миграция (#9) требует отдельной wiring-волны
**Контекст:** Spy-Bot: aiogram 2->3 + sync->async + GPT->Gemini = 3 миграции одновременно. Wiring-агент: 48 tool uses.
**Урок:** При множественных миграциях wiring (связывание модулей, imports, __init__.py) = САМЫЙ трудоёмкий этап. 48 tool uses — нормальная цена интеграции 30+ файлов от 5 агентов. Wiring-агент = отладчик, не разработчик. Без отдельного wiring-этапа каждый агент пытается чинить чужие импорты = конфликты.
**Применение:** Для миграций: отдельная Wave для wiring ПОСЛЕ всех параллельных агентов. Бюджетировать 40-60 tool uses.

### EXP-023 (PAT-012): ВСЕ 10 триггеров = максимальная валидация системы
**Контекст:** Spy-Bot — первый проект с 10/10 триггеров. Каждый нашёл реальную проблему.
**Урок:** Система триггеров EA работает как чек-лист: чем больше триггеров сработало, тем выше сложность проекта и тем важнее следовать рекомендациям. Compound Engineering (план -> волны -> gates -> тесты) окупается экспоненциально при 5+ триггерах. При 10 триггерах без плана = гарантированный хаос.
**Применение:** При 5+ одновременных триггерах — переход от Advisory к Recommended для всех. При 8+ — Compound Engineering обязателен.

**Урок:** MS Store Python не включает компилятор C. TgCrypto требует native compilation. Решение: батник с `vcvarsall.bat` из Visual Studio Build Tools перед pip install.
**Применение:** При работе с Pyrogram на Windows — проверять наличие Build Tools. Если нет — использовать батник или устанавливать Python с python.org (не из MS Store).

**Урок:** Для userbot авторизации: SMS как primary, QR-код как fallback при FloodWait. QR auth не триггерит flood protection. Паттерн: try SMS → except FloodWait → switch to QR.

### EXP-030 (FIX-SPY-004): Race condition — asyncio.gather до готовности БД

**Контекст:** `asyncio.gather(bot_start, userbot_start)` запускал компоненты до завершения `db.init()`. Хаотичные ошибки "table doesn't exist".
**Урок:** Shared resources (БД, кэш, конфиги) ОБЯЗАТЕЛЬНО инициализировать ДО `asyncio.gather()`. Порядок: `await db.init()` → `await asyncio.gather(...)`. Race condition при параллельном старте = классическая ошибка инициализации.
**Применение:** Шаблон для старта многокомпонентных ботов: сначала все shared init по очереди (await), потом параллельный запуск компонентов через gather.

**Триггеры:** #3 (бизнес-логика), #6 (3+ задач), #10 (фича 3+ файлов)

### Уроки
1. **SQLite VACUUM требует переоткрытия соединения** — aiosqlite не поддерживает VACUUM в-рамках текущего соединения. Паттерн: close → new connect → VACUUM → close → reopen + restore row_factory.
2. **Транзакционная архивация** — INSERT INTO archive SELECT... + DELETE FROM main в одном блоке. FTS5 триггеры автоматически чистят индекс при DELETE — не нужно ручное обслуживание.
3. **dict.get() NoneType ловушка** — `d.get("key", "default")` вернёт None если ключ есть со значением None. Паттерн: `(d.get("key") or d.get("fallback") or "")`.
4. **approval sync → scheduler async мост** — approval._execute_action() синхронный, database методы async. Решение: approval ставит флаг "approved", scheduler в async loop находит и выполняет.

### EXP-032 (FIX-004): FTS5 split(";") — молчаливый баг в production
- **Дата:** 2026-02-19
- **Проект:** 05-client-bot (Marsel Luxury)
- **Сигнал:** #3 (бизнес-логика) + #4 (безопасность)
- **Проблема:** `SCHEMA_SQL.split(";")` ломал SQL триггеры содержащие `;` внутри `BEGIN...END`. Ошибки глотались `except Exception`. FTS5 индекс никогда не заполнялся — поиск по каталогу полностью не работал.
- **Решение:** Заменить `split(";")` + поштучный `execute()` на `executescript()`
- **Урок:** НИКОГДА не разбивать SQL по `;` вручную если есть триггеры/процедуры. Использовать `executescript()` или парсер. Bare `except Exception` в схеме БД = БОМБА — ошибки создания таблиц/триггеров проходят молча.
- **Паттерн:** Signal #3 подтверждён — тесты на бизнес-логику (FTS5 поиск) нашли production-баг до деплоя.

### EXP-033 (FIX-005): Hardcoded credentials в 3 файлах одновременно
- **Дата:** 2026-02-19
- **Проект:** 05-client-bot (Marsel Luxury)
- **Сигнал:** #4 MANDATORY (безопасность)
- **Проблема:** Реальные токены найдены в 3 местах: config_old.py (Telegram token), db.py (YooKassa credentials), bot/.env (дубликат токена). ADMIN_USER_IDS имел hardcoded default.
- **Решение:** Удалить все 3 файла, убрать hardcoded default, отозвать токены.
- **Урок:** При аудите безопасности искать credentials НЕ в одном файле, а grep по ВСЕМУ проекту. Паттерны: token, secret, key, password, IBAN, credential.

### Уроки (сводка)
1. **split(";") = anti-pattern для SQL с триггерами** — executescript() или парсер. Bare except = бомба замедленного действия.
2. **Grep по всему проекту при аудите безопасности** — credentials прячутся в 3+ местах одновременно. Один файл = ложная безопасность.

### EXP-035 (FIX-RASSILKA-001): Async Migration — все call sites требуют await (2026-02-19)

**Контекст:** Rassilka Bot v3.0, миграция sync → aiosqlite. 92 missing await в 3 файлах handlers/
**Проблема:** При конвертации sync-функций в async НЕДОСТАТОЧНО изменить `def → async def` и добавить await в теле функции. ОБЯЗАТЕЛЬНО нужно найти ВСЕ call sites и добавить await туда.
- Было: `def get_user(id): return db.query(...)`
- Стало: `async def get_user(id): return await db.query(...)`
- Забыли: Все вызовы `user = get_user(id)` в других файлах должны стать `user = await get_user(id)`

**Результат:** Runtime crash `TypeError: coroutine object is not subscriptable` при попытке обратиться к результату функции
**Почему тесты не нашли:** Если unit-тесты тестируют слой изолированно (мокируют DB), они не поймут что функция вернула coroutine. Нужны integration-тесты с реальным await.

**Решение:**
1. **AST-based scan:** grep `await\s+get_user` покажет все места где забыли await
2. **Manual check:** "def get_user" → в статических анализаторах (pylint, mypy) с `--no-implicit-optional` выловит coroutines
3. **Integration tests:** КАЖДАЯ async функция должна быть использована с await в минимум одном тесте

**Правило:** Триггер #9 (миграция sync→async) требует **обязательного** этапа "полный grep по всем call sites" перед финальным QA. Один пропущенный await = гарантированный crash в production.

### EXP-036 (FIX-RASSILKA-002): God Object Refactoring — __init__.py reexports (2026-02-19)

**Контекст:** Rassilka Bot, разделение монолита db.py на пакет bot/db/
**Проблема:** Разбили `db.py` → `bot/db/models.py`, `bot/db/queries.py`, `bot/db/migrations.py`. Создали `bot/db/__init__.py`, но забыли реэкспортировать функции.

**Результат:** Все существующие импорты `from bot.db import UserModel, get_user, init_db` сломались с `ImportError: cannot import name 'get_user'`

**Что произошло:**
```python
# старый код ожидал

# но после рефакторинга было
# bot/db/__init__.py (пустой или с частичным импортом)
```

**Решение:**
```python
# bot/db/__init__.py ДОЛЖЕН содержать
from .models import UserModel, Campaign, Message  # все модели
from .queries import (  # все функции
    get_user, create_user, update_user, delete_user,
    get_campaign, create_campaign, launch_campaign,

    'UserModel', 'Campaign', 'Message',
    'get_user', 'create_user', 'update_user', 'delete_user',
    'get_campaign', 'create_campaign', 'launch_campaign',
    'get_message', 'log_message', 'archive_message',

```

**Правило:** При разделении монолита на пакет: `__init__.py` реэкспортирует ВСЕ public API. Если в старом коде было `from module import X`, то в новом `from module.subpackage import X` должна работать ТОЧНО ТАК ЖЕ.

**Backward-compatibility:** Включать и legacy имена функций если они были переименованы:
```python

```

### EXP-037 (FIX-RASSILKA-003): QA Gate Check Pattern — между фазами рефакторинга (2026-02-19)

**Контекст:** Rassilka Bot, 5 волн рефакторинга. Gate Check поймал 92 missing await (которые unit-тесты пропустили).

**Проблема:** Разработка 5 волн параллельно или последовательно, но БЕЗ проверок между ними. Результат: волна 3 ломает волну 1, но это обнаруживается только в конце.

**Решение: Обязательная QA-проверка между волнами**

**Checklist Gate Check:**
- [ ] Syntax errors: `python -m py_compile *.py` (все файлы компилируются?)
- [ ] Imports: `python -c "import bot; import bot.handlers"` (все модули импортируются?)
- [ ] Await consistency: `grep -r "async def" . | grep -v "await"` (все async функции вызываются с await?)
- [ ] Callback conflicts: grep все `@router.message` на дублирование (одна команда не обработана 2 раза?)
- [ ] Tests passing: `pytest --tb=short` (базовые тесты проходят?)
- [ ] Regression: `pytest test_regression.py` (старые фичи не сломались?)

**Пример Gate Check Script:**
```bash
#!/bin/bash
set -e
echo "Gate Check: syntax..."
python -m py_compile bot/**/*.py
echo "Gate Check: imports..."
python -c "import bot" && echo "  ✓ Bot imports OK"
echo "Gate Check: await..."
MISSING=$(grep -r "= get_" bot/handlers | grep -v "= await get_" | wc -l)
if [ $MISSING -gt 0 ]; then
  echo "  ✗ Found $MISSING missing await"
  grep -r "= get_" bot/handlers | grep -v "= await get_"
  exit 1
fi
echo "Gate Check: tests..."
pytest -q && echo "  ✓ Tests pass"
echo "✓ All gates passed"
```

**Результат в rassilka-bot:** Gate Check поймал 92 missing await ДО deплоя. Без gate — это был бы production crash.

**Правило:** При 3+ волнах рефакторинга или 2+ параллельных агентов → обязательный Quality Gate между этапами.

### EXP-038 (PAT-019): Shared Session Pattern — aiohttp.ClientSession singleton (2026-02-19)

**Контекст:** Rassilka Bot, UltraMSG API для WhatsApp, 9 волн с параллельным использованием API.

**Проблема:** Каждый handler создавал `async with aiohttp.ClientSession()` → 50+ сессий в памяти одновременно. Memory leak, медленные запросы.

**Решение: Singleton session**

**В aiogram (есть dp — dispatcher):**
```python
# main.py
from aiohttp import ClientSession

async def main():
    session = ClientSession()
    dp["session"] = session  # DI injection

    # в handlers:
    async def send_message(message: Message):
        session = message.bot["session"]  # достаём из DI
        async with session.post(...) as resp: ...

    # cleanup:
    await dp.feed_shutdown()  # сработает при graceful shutdown
    await session.close()
```

**Для scheduler (нет dp):**
```python
# Scheduler — своя очередь инициализации
async def send_scheduled_campaign():
    # Создаём temporary session с cleanup
    session = ClientSession()
    try:
        async with session.post(UltraMSG_URL, ...) as resp:
            await handle_response(resp)
    finally:
        await session.close()

# ИЛИ (если много запросов в scheduler):
_scheduler_session = None

async def get_scheduler_session():
    global _scheduler_session
    if _scheduler_session is None:
        _scheduler_session = ClientSession()
        # cleanup регистрируем где-то в shutdown
    return _scheduler_session
```

**Паттерны reuse:**
- **DI через dp["key"]** — для всего что есть Dispatcher
- **Global singleton с cleanup** — для компонентов без dp (scheduler, background tasks)
- **Temporary session** — если всего 1-2 запроса, создать → использовать → закрыть
- **Connection pool** — для 100+ запросов в минуту, использовать параметры SessionConnector

**Правило:** Никогда не создавать ClientSession в функции, которая вызывается 100+ раз в час. Один session на приложение + graceful shutdown.
