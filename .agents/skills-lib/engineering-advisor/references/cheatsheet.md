# Шпаргалка: Инженерные практики для вайб-кодера v4.0

> Копируй нужный промпт и добавляй к своему запросу в Claude.

---

## 1. Копируй-вставляй промпты

### Когда получил сгенерированный код (> 50 строк)

Ты получил большой кусок кода и не понимаешь что там происходит. Прежде чем вставлять — разберись.

```
Объясни что делает каждая функция простыми словами прежде чем я вставлю.
Для каждой функции: название → что принимает → что делает → что возвращает.
Без жаргона, как будто объясняешь менеджеру.
```

---

### Когда нужны тесты

Код делает что-то важное (считает деньги, отправляет данные, принимает решения). Тесты — это проверка, что код работает как надо.

```
Напиши тесты к этой функции: нормальный ввод, неправильный ввод, граничные случаи (пусто, ноль, очень большое число). Запусти тесты и покажи результат.
```

---

### Когда ошибка не уходит (3+ попыток)

Ты уже три раза просил исправить баг, а он возвращается в новом виде. Заплатки поверх заплаток не работают.

```
СТОП. Не латай. Перепиши этот файл с нуля чисто, сохрани функциональность, добавь тесты. Объясни что было не так в старом варианте.
```

---

### Когда код касается оплаты / безопасности

Код работает с деньгами, паролями, персональными данными или API-ключами. Ошибка здесь = реальные убытки.

```
Это касается оплаты. Сначала ревью на безопасность, потом тесты, потом реализация. Не пропускай. Проверь: нет ли утечки ключей, правильная ли валидация сумм, есть ли обработка ошибок платёжного шлюза.
```

---

### Когда несколько независимых задач

У тебя 3-5 задач, которые не зависят друг от друга. Можно делать параллельно.

```
Эти задачи независимые. Запусти параллельно отдельными агентами. Задачи: 1) ... 2) ... 3) ...
```

---

### Когда нужен рефакторинг

Код работает, но читать его невозможно. Функция на 200 строк, копипаста повсюду, непонятные имена переменных.

```
Перепиши эту функцию с нуля с чётким планом. Не патчь. Разбей на маленькие функции с понятными именами. Добавь тесты, чтобы убедиться что ничего не сломалось.
```

---

### Когда нужна проверка результата

Claude говорит "должно работать" или "это решит проблему". Слова — не доказательство.

```
Запусти код и покажи РЕАЛЬНЫЙ результат. Не "должно работать", а фактический вывод. Если есть ошибки — покажи их тоже.
```

---

### Когда нужен план перед кодом

Сложная задача, много файлов, непонятно с чего начать. План экономит часы переделок.

```
Прежде чем кодить — напиши план из 5-7 шагов. Каждый шаг = одна задача. Укажи: что делаем, какие файлы трогаем, как проверяем что шаг выполнен.
```

---

### Когда начинаешь сложный проект

Проект с несколькими компонентами (фронт + бэк, бот + база, несколько интеграций).

```
Используй скилл командная-работа для этого проекта. Раздели на подзадачи, назначь агентов, координируй.
```

---

### Когда ошибка возвращается (петля ошибок)

Ты уже "исправлял" эту ошибку, но она снова здесь. Или фикс одной ошибки создал новую. Случайные правки не работают — нужен диагноз.

```
Не чини наугад. Найди корневую причину ошибки: 1) что именно ломается, 2) почему именно это ломается, 3) где первоисточник проблемы. Потом предложи решение.
```

---

### #19 — Порядок хэндлеров в фреймворке

```
Проверь порядок регистрации хэндлеров: 1) Command() хэндлеры до F.text catch-all? 2) Конкретные callback_data= до F.data catch-all? 3) Middleware order правильный? Покажи порядок регистрации.
```

---

### #20 — Блокирующие вызовы в async

```
Найди ВСЕ блокирующие вызовы в async-коде: 1) time.sleep → asyncio.sleep, 2) requests.get/post → aiohttp.ClientSession, 3) sync DB → async DB driver. Покажи список найденных и замени каждый.
```

---

### #21 — Пропущенный callback.answer()

```
Проверь все CallbackQuery handlers: каждый вызывает callback.answer()? Если нет -- добавь. Можно с текстом (callback.answer('Готово!')) или без (callback.answer()). Главное -- вызвать.
```

---

### #22 — Большой монолитный файл

```
Файл слишком большой ([N] строк). Предложи план разделения: 1) группы функций по ответственности, 2) какие файлы создать, 3) что вынести в каждый, 4) как сохранить импорты через __init__.py. Не разделяй -- сначала план.
```

## 3. Красные флаги AI

Что говорит Claude и что это реально значит.

| Claude говорит | Что это значит | Твой ответ |
|---------------|---------------|------------|
| "Должно работать" | Не проверял. Теория, не факт | "Запусти и покажи реальный вывод" |
| "Я исправил ошибку" (3-й раз) | Латает заплатками, корень не найден | "СТОП. Перепиши с нуля" |
| "Вот полный код" (300+ строк) | Может содержать неочевидные баги | "Объясни каждую функцию, потом тесты" |
| "Это простое изменение" | Может сломать что-то рядом | "Покажи что ещё затрагивает это изменение" |
| "Готово!" (без запуска) | Не факт что работает | "Запусти тесты и покажи результат" |
| "Добавил обработку ошибок" | Может быть пустой try/catch | "Покажи что именно происходит при каждой ошибке" |
| "Оптимизировал код" | Мог изменить логику | "Покажи что результат такой же как был. Запусти старые тесты" |
| "Безопасно" (про оплату/данные) | Нужна конкретная проверка | "Покажи конкретно: где валидация, где шифрование, где логирование" |

## 4. Аналогии: технические термины простыми словами

| Термин | Аналогия из жизни |
|--------|-------------------|
| **Тесты** | Чек-лист перед сдачей отеля гостям. Вода идёт? Кондиционер работает? Wi-Fi ловит? Если не проверить — гость найдёт проблему за тебя |
| **Рефакторинг** | Генеральная уборка в офисе. Всё работает, но бумаги в кучах, найти ничего невозможно. После уборки — те же документы, но каждый на своём месте |
| **Code review** | Коллега проверяет твой маршрут экскурсии: не забыл ли остановку, хватит ли времени, нет ли пробки. Свежие глаза видят то, что ты пропустил |
| **TDD (Test-Driven Development)** | Сначала пишешь чек-лист "что должна включать экскурсия", потом составляешь маршрут. Не наоборот |
| **Баг** | Клиент забронировал яхту на 15:00, а в системе записалось 03:00. Маленькая ошибка, большие проблемы |
| **Дебаггинг** | Клиент жалуется что трансфер не приехал. Ты проверяешь: заказ есть? Водителю ушло? Адрес правильный? Телефон верный? Идёшь по цепочке пока не найдёшь где оборвалось |
| **API** | Стойка ресепшена в отеле. Ты не ходишь на кухню сам — просишь через стойку. API = стойка между твоим кодом и чужим сервисом |
| **Git** | Машина времени для кода. Сохраняешь состояние, и если сломал — откатился на вчера. Без Git = работа без автосохранения |
| **Параллельные агенты** | Вместо одного гида на 5 групп — 5 гидов, каждый ведёт свою группу одновременно |
| **CI/CD** | Автоматический контроль качества на фабрике. Каждая деталь проходит проверку перед тем как попасть в коробку |
| **Переменные** | Бирки на чемоданах. `clientName = "Марат"` — бирка "clientName", на чемодане написано "Марат". Завтра бирку можно повесить на другой чемодан |
| **Функция** | Готовый маршрут экскурсии. Говоришь "сафари-тур" — и запускается вся цепочка: пикап, джип, дюны, ужин, возврат. Не объясняешь каждый раз заново |

## 5. Три уровня — когда какой

### Advisory (зелёный) — совет

Для некритичных ситуаций. Можно пропустить без последствий.

**Примеры:**
- "Этот код можно разбить на функции поменьше — будет читаемее"
- "Есть возможность запустить эти задачи параллельно"
- "Можно добавить комментарии для ясности"

**Когда пропускать:** одноразовый скрипт, эксперимент, прототип.

---

### Recommended (жёлтый) — настоятельная рекомендация

Для ситуаций с реальным риском потери времени. Пропуск = вероятные проблемы потом.

**Примеры:**
- "Эта функция не имеет тестов, а от неё зависит другой код"
- "Ошибка возвращается третий раз — нужна пересборка вместо патчей"
- "Этот код сложный, лучше составить план перед написанием"

**Когда пропускать:** ты понимаешь риск и сознательно принимаешь решение ускориться.

---

### MANDATORY (красный) — обязательно

Только для ситуаций где ошибка = реальные убытки или утечка данных.

**Примеры:**
- "Код обрабатывает платежи — обязательно ревью + тесты"
- "API-ключи в открытом виде в коде — исправить немедленно"
- "Пароли хранятся без шифрования — критическая уязвимость"

**Когда пропускать:** НИКОГДА. Если хочется пропустить — перечитай, почему это красный уровень.

## Быстрые grep-команды (aiogram)

| Проверка | Команда |
|----------|---------|
| Блокирующие вызовы | `grep -rn "time\.sleep\|requests\.get\|requests\.post" --include="*.py"` |
| Deprecated bot["key"] | `grep -rn "bot\[" --include="*.py"` |
| Старый синтаксис v2 | `grep -rn "message_handler\|callback_query_handler" --include="*.py"` |
| Большие файлы | `wc -l *.py **/*.py 2>/dev/null \| sort -rn \| head -5` |
| Порядок хэндлеров | `grep -n "F\.text\|Command(" handlers/*.py \| sort -t: -k2 -n` |

## Субагентный шаблон (минимум)

Вставляй в каждый Task tool call при делегации кода:
```
1. БЭКАП: Перед Edit/Write — копия в backups/
2. ТЕСТЫ: MagicMock(spec=RealClass)
3. DATACLASS: Сверить .field с @dataclass
4. AIOGRAM: Command() ВЫШЕ F.text catch-all
5. ASYNC: Нет time.sleep/requests.get в async
6. HTML: html.escape() на пользовательский ввод
7. CALLBACK: callback.answer() в каждом handler
8. ВЕРИФИКАЦИЯ: pytest -x после изменений
```
