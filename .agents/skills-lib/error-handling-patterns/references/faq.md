# FAQ — error-handling-patterns

## Q1: Когда использовать exceptions, а когда Result-типы?
**Exceptions** — для неожиданных ситуаций, которые нарушают нормальный поток (сбой БД, corrupted data, programming bugs). **Result-типы** (Result<T, E> в Rust, Either в Scala, custom в TS) — для ожидаемых ошибок, которые являются частью бизнес-логики (невалидный ввод, ресурс не найден, нарушение бизнес-правил). Правило: если вызывающий код должен обязательно обработать ошибку — Result. Если это аварийная ситуация — exception.

## Q2: Стоит ли создавать кастомные классы ошибок?
Да, но разумно. Создавайте иерархию:
- `AppError` (базовый) -> `ValidationError`, `NotFoundError`, `AuthError`, `ExternalServiceError`
- Каждый класс содержит: код, сообщение для разработчика, сообщение для пользователя, контекст
- Не создавайте класс на каждую ситуацию — группируйте по типу обработки
- В TypeScript/JavaScript: расширяйте `Error`, сохраняйте `name` и `stack`

## Q3: Как правильно логировать ошибки?
Уровни:
- `ERROR` — требует внимания: необработанные исключения, сбои внешних сервисов, потеря данных
- `WARN` — подозрительно, но обработано: retry succeeded, fallback activated, deprecated usage
- `INFO` — ожидаемые ошибки бизнес-логики: невалидный ввод, 404
- `DEBUG` — детали для отладки: стэктрейс повторных попыток, содержимое запроса

Обязательно включайте: correlation ID, timestamp, контекст (user_id, request_id), стэктрейс (для ERROR). Никогда не логируйте пароли, токены, PII.

## Q4: Когда применять retry, а когда fail fast?
**Retry** — для транзиентных ошибок: сетевой таймаут, 503, connection refused, lock timeout. Обязательно с exponential backoff и jitter. Максимум 3-5 попыток.
**Fail fast** — для детерминированных ошибок: 400, 401, 403, 422, validation errors. Повтор не изменит результат — сразу возвращайте ошибку.

## Q5: Что такое Circuit Breaker и когда его использовать?
Circuit Breaker — паттерн для защиты от каскадных сбоев при работе с внешними сервисами. Три состояния:
- **Closed** (норма) — запросы проходят, считаются ошибки
- **Open** (сбой) — все запросы сразу возвращают ошибку без обращения к сервису
- **Half-Open** (проба) — пропускается один запрос для проверки восстановления

Используйте, когда: зависите от внешнего сервиса, который может быть недоступен; хотите избежать каскадных сбоев; нужен быстрый fallback вместо долгих таймаутов.
