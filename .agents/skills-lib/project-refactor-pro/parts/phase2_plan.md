# Phase 2: PLAN

## Цель

Превратить сырой SCAN Report из Phase 1 в конкретный, утверждённый пользователем план действий. Ни один файл не перемещается и не переименовывается до получения явного OK.

---

## Пошаговый workflow

### Step 1. Получить SCAN Report

Прочитать отчёт Phase 1. Извлечь:
- Полный список файлов (пути, типы, размеры, даты)
- Обнаруженные проблемы (дубликаты, мёртвый код, нарушения структуры)
- Текущее дерево каталогов

### Step 2. Сгруппировать файлы по назначению

Распределить каждый файл в одну из категорий:

| Категория | Примеры |
|-----------|---------|
| **code** | `.py`, `.js`, `.ts`, `.html`, `.css` — исходный код |
| **docs** | `.md`, `.txt`, `.pdf` — документация, гайды, заметки |
| **assets** | Изображения, шрифты, иконки, видео |
| **config** | `.json`, `.yaml`, `.env`, `.gitignore`, `Dockerfile` |
| **archive** | Устаревшие версии, бэкапы, файлы не тронутые 6+ месяцев |
| **unknown** | Файлы, не попадающие ни в одну категорию — требуют решения пользователя |

Внутри каждой категории дополнительно группировать по подназначению (например, code: backend vs frontend; docs: guides vs reports).

### Step 3. Предложить новую структуру папок

Построить ASCII-дерево целевой иерархии. Правила:

- Имена папок: `snake_case` или `kebab-case`, без пробелов
- Файлы с датами: `YYYY-MM-DD_description.ext`
- Глубина вложенности: максимум 3 уровня (исключение — монорепо)
- Каждая папка должна иметь ясное единственное назначение
- `_archive/` — для устаревших файлов (не удалять, а архивировать)

Пример формата:

```
project/
├── src/
│   ├── backend/
│   ├── frontend/
│   └── shared/
├── docs/
│   ├── guides/
│   └── reports/
├── assets/
│   ├── images/
│   └── fonts/
├── config/
├── scripts/
├── tests/
└── _archive/
```

### Step 4. Создать таблицу перемещений

Для каждого файла/группы файлов указать:

```markdown
| # | Текущий путь | Новый путь | Действие | Примечание |
|---|-------------|-----------|----------|------------|
| 1 | src/utils.py | src/shared/utils.py | move | Общий модуль |
| 2 | old_handler.py | _archive/old_handler.py | archive | Не используется с 2025-08 |
| 3 | README (1).md | — | delete | Дубликат README.md |
| 4 | photo cover.html | photo_cover.html | rename | Пробел в имени |
```

Действия: `move`, `rename`, `archive`, `delete`, `merge`, `keep` (оставить как есть).

Файлы, помеченные `delete` — выделить отдельно для явного подтверждения.

### Step 5. Определить ссылки для обновления

Просканировать все файлы на наличие ссылок, которые сломаются при перемещении:

| Тип ссылки | Где искать | Паттерн поиска |
|-----------|-----------|---------------|
| HTML src/href | `.html` файлы | `src="..."`, `href="..."` |
| CSS url() | `.css` файлы | `url(...)`, `@import` |
| Markdown links | `.md` файлы | `[text](path)`, `![img](path)` |
| Python imports | `.py` файлы | `import`, `from ... import` |
| JS/TS imports | `.js`, `.ts` | `import`, `require()` |
| Config paths | `.json`, `.yaml` | Строковые значения с путями |

Для каждой ссылки указать:
- Файл-источник (где стоит ссылка)
- Текущее значение
- Новое значение после перемещения

### Step 6. Оценить архитектуру кода (для code-файлов)

Применить концепцию **Deep Modules** (John Ousterhout):

> Глубокий модуль = маленький интерфейс, большая реализация.
> Мелкий модуль = интерфейс почти такой же сложный, как реализация.

**6a. Оценить глубину модулей:**

Для каждого значимого модуля/файла:
- Посчитать количество экспортируемых функций/классов (= размер интерфейса)
- Посчитать строки реализации (= объём скрытой сложности)
- Отношение реализации к интерфейсу = "глубина"

**6b. Найти кандидатов на объединение:**

Тесно связанные модули — кандидаты на слияние в один глубокий модуль:
- Модули, которые всегда импортируются вместе
- Модули, разделяющие одни и те же типы/структуры данных
- Модули, где понимание одного требует чтения другого
- Мелкие утилиты, извлечённые "для тестируемости", но тестирующие не то

Формат предложения:

```markdown
### Объединение: {module_a} + {module_b} → {new_module}

**Почему связаны:** Общие типы, всегда импортируются вместе
**Текущий интерфейс:** 12 функций суммарно
**Предлагаемый интерфейс:** 4 функции
**Скрытая сложность:** вся логика валидации и трансформации
**Влияние на тесты:** 8 unit-тестов → 4 boundary-теста
```

**6c. Для тяжёлых рефакторингов — RFC:**

Если объединение затрагивает >5 файлов или >500 строк:
- Создать RFC как GitHub Issue (через `gh issue create`)
- Шаблон: проблема → предлагаемое решение → затронутые файлы → план миграции
- Не блокировать остальной план — RFC идёт параллельно

### Step 7. Показать план пользователю

Собрать финальный план в единый документ:

```markdown
# Refactor Plan: {project_name}

## Текущее состояние
- Всего файлов: X
- Категории: code (N), docs (N), assets (N), config (N), archive (N)
- Проблемы: [из SCAN Report]

## Предлагаемая структура
[ASCII tree из Step 3]

## Перемещения и переименования
[Таблица из Step 4]

## Ссылки для обновления
[Таблица из Step 5]
Всего ссылок для обновления: N

## Архитектурные предложения (код)
[Из Step 6 — объединения модулей, если применимо]

## Файлы, требующие вашего решения
- [Список unknown файлов и файлов на удаление]

## Порядок выполнения
1. Создать новые папки
2. Переместить/переименовать файлы
3. Обновить все ссылки
4. Архивировать устаревшее
5. Удалить дубликаты (после подтверждения)
6. [Если есть] Применить архитектурные объединения

---
Утвердить план? (да / нет / изменить)
```

---

## Критические правила

1. **НИКОГДА не выполнять перемещения без явного "да" от пользователя**
2. Файлы в `unknown` категории — всегда спрашивать, не угадывать
3. Удаления (`delete`) показывать отдельным списком с объяснением причины
4. Rename-конвенции: `snake_case` для кода и путей, `YYYY-MM-DD` для дат в именах
5. Сохранять оригинальные даты модификации при перемещении
6. Архивировать вместо удаления при любом сомнении
7. RFC для тяжёлых рефакторингов — не пытаться сделать всё в одном шаге
8. Если проект использует Git — учитывать `.gitignore` и не ломать историю (rename detection работает при >50% совпадении содержимого)

## Выход Phase 2

Утверждённый пользователем **Refactor Plan** — входной документ для Phase 3 (EXECUTE).
