## Заполненный пример

# ADR-001: Synthetic user_id strategy для Max Bot

**Status:** Proposed
**Date:** 2026-03-12
**Deciders:** Сухейль, архитектор CatalogBot

---

## Context

CatalogBot работает с PostgreSQL таблицей `loyalty`, которая хранит единый профиль пользователя вне зависимости от платформы. Поле `user_id` — BIGINT и является первичным ключом.

Telegram использует реальные числовые user_id (1..10^10). VK использует реальные user_id со смещением +10,000,000,000 (чтобы не пересекаться с Telegram). Для webhook-платформ (Instagram, WhatsApp, Facebook, Viber) user_id — строка (PSID, phone number, Viber user_id), поэтому для них создаётся "synthetic" числовой user_id.

Текущие диапазоны:
- Instagram: -1 .. -999 (до 999 пользователей)
- WhatsApp: -1000 .. -1999
- Facebook: -2000 .. -2999
- Viber: -3000 .. -3999

Max Bot — новая платформа с строковым user_id. Нужно выбрать диапазон.

Ограничение: `loyalty.user_id` — BIGINT SIGNED, минимальное значение -9,223,372,036,854,775,808. Места хватит на тысячи диапазонов.

## Decision

> Использовать диапазон -4000..-4999 для Max Bot. Добавить константу `MAX_ID_OFFSET = -4000` в `core/user_ids.py`.

## Consequences

### Positive
- Полная согласованность с существующим паттерном (все webhook-платформы → отрицательные, шаг 1000)
- Легко читаемо: `user_id = -4217` → сразу понятно что это Max Bot пользователь
- `get_platform(user_id)` в `core/user_ids.py` получает простое условие: `elif -4999 <= uid <= -4000`
- Нулевые конфликты с существующими диапазонами

### Negative / Trade-offs
- Лимит 1000 Max Bot пользователей на synthetic range
  - Смягчение: если Max Bot станет массовым → расширим диапазон до -4000..-49999 миграцией
- При добавлении 8-й платформы — следующий диапазон -5000..-5999 (не автоматически)

### Neutral
- Нужно обновить docstring в `core/user_ids.py` с новым диапазоном
- Нужно добавить `max` в `get_platform()` elif цепочку
- README/CLAUDE.md обновить таблицу User ID разделения

## Alternatives Considered

### Option A: Диапазон -10000..-10999 (пропустить с запасом)
- Описание: Оставить -4000..-9999 зарезервированными для будущих платформ
- Плюсы: Явный gap для будущих платформ
- Минусы: Создаёт "дырки" без назначения, усложняет `get_platform()` (нужен range check с gap)
- Отклонён потому что: принцип consistency важнее — все платформы идут подряд без пропусков

### Option B: Положительный offset как у VK (+40,000,000,000)
- Описание: Max Bot user_id хранить как real_id + 40B
- Плюсы: Почти неограниченное количество пользователей
- Минусы: Нарушает единообразие — IG/WA/FB/Viber все используют отрицательные; строковые Max Bot ID нельзя напрямую конвертировать в числа
- Отклонён потому что: webhook-платформы = отрицательные synthetic, это устоявшийся паттерн

### Option C: Отдельная таблица ID маппинга без synthetic_user_id
- Описание: Не использовать loyalty.user_id для Max Bot; создать отдельную identity table
- Плюсы: Нет ограничений на диапазоны
- Минусы: Сломает всю существующую бизнес-логику (loyalty points, bookings, analytics — всё через user_id); огромный рефакторинг
- Отклонён потому что: цена изменения несопоставимо выше выгоды

## ADR Quick Reference

| Статус | Значение |
|--------|----------|
| `Proposed` | Написан, ещё не согласован |
| `Accepted` | Согласован и активен |
| `Deprecated` | Больше не актуален, но не заменён |
| `Superseded by ADR-NNN` | Заменён более новым ADR |

**Когда точно нужен ADR:**
- Выбор между двумя технологиями / подходами
- Решение о паттерне хранения данных
- Выбор стратегии авторизации
- Любое "почему мы так сделали?" которое всплывёт через полгода
- Изменение, которое трудно откатить

**Когда ADR НЕ нужен:**
- Тривиальные правки кода
- Следование уже принятому паттерну (просто укажи ссылку на паттерн)
- Временные решения, которые точно изменятся через 2 недели
