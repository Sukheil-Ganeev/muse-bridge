# VIP-DXB-RUS UI Prototyper

Скилл для быстрого создания luxury HTML-прототипов с 3 вариантами дизайна.

## Обязательно: использовать вместе с /frontend-design

При создании прототипа ВСЕГДА активировать скилл `frontend-design` — он даёт 10 эстетических архетипов, CSS-токены, anti-pattern guidance и 5-point quality checklist. Наш архетип: **Editorial/Magazine + Minimalist** (Swiss typography, generous spacing, serif display type, micro-contrast).

## Когда использовать

- Владелец хочет увидеть варианты дизайна перед кодом
- Нужно переделать существующий элемент (кнопка, панель, модал)
- Новая фича требует визуального решения
- Владелец говорит "мне не нравится" — значит нужен прототип

## Workflow

### Шаг 1: Загрузить справочник

Прочитать `references/design-bible.md` — единый справочник с:
- Цветами, шрифтами, стилями бренда
- Предпочтениями владельца (что нравится / раздражает)
- Конкурентами и референсами
- Breakpoints для всех устройств
- Готовым CSS template для копирования

НЕ читать отдельные файлы (brand-identity.md, personalization.md и т.д.) — всё уже в справочнике.

### Шаг 2: Понять задачу

Уточнить у владельца:
- Какой элемент прототипируем?
- Что именно не нравится в текущем?
- Есть ли пример "как хочется" (сайт, скриншот)?

Владелец НЕ программист — задавать вопросы простым языком.

### Шаг 3: Исследование (если нужно)

Если элемент сложный (навигация, фильтры, модал):
- Прочитать текущий компонент на сайте
- WebSearch: как это делают luxury-сайты (Four Seasons, Aman, Net-a-Porter)
- Посмотреть прототип — referenceы из design-bible.md

### Шаг 4: Создать прототип

Файл: `D:/Downloads/vipdxbrus-website/docs/prototypes/{название}-prototype.html`

**Обязательная структура:**

```
┌─ Header (тёмный, VIP·DXB·RUS, табы A/B/C)
├─ Описание варианта (border-left copper)
├─ Основной контент варианта
│   ├─ Desktop view
│   └─ Контекст (карточки/фото для реалистичности)
├─ [Повторить для каждого варианта]
└─ Responsive: работает на всех размерах
```

**3 варианта — всегда:**
- Вариант A: Консервативный (минимальные изменения, проверенный подход)
- Вариант B: Оптимальный (баланс красоты и функциональности)
- Вариант C: Смелый (новаторский, может удивить)

Табы переключают варианты. Каждый вариант имеет:
- Заголовок (Tenor Sans, uppercase)
- Описание простым языком (что это, как работает)
- Интерактивный demo

**Обязательные элементы HTML:**
- Google Fonts: Tenor Sans, Montserrat, Cormorant SC (точный URL из design-bible)
- CSS variables из design-bible (скопировать блок CSS Template)
- Реальные Unsplash фото Дубая
- SVG иконки inline (не emoji, не img)
- border-radius: 0 везде (кроме pill CTA и circular)
- Русский язык
- Интерактивность (клики, hover, toggle, анимации)

**Responsive breakpoints (тестировать все):**

| Устройство | Ширина |
|-----------|--------|
| iPhone SE | 375px |
| iPhone 14 | 390px |
| iPhone 15 Pro Max | 430px |
| Samsung S24 | 360px |

| iPad Pro | 1024px |

### Шаг 6: Feedback → Итерация

Владелец выбирает вариант или комбинацию. Типичные ответы:
- "Мне нравится B" → Утвердить B, перейти к реализации
- "A + B" → Объединить лучшее из обоих в новый вариант
- "Не нравится ничего" → Уточнить что именно, сделать новые 3

После одобрения прототип становится визуальным ТЗ для кода.

## Правила качества

### Pixel-perfect
- Одинаковые отступы, выравнивание, размеры
- Без "почти" — точно как задумано
- Проверять на минимум 3 breakpoints

### Luxury ≠ перегруженность
- Меньше элементов, больше пространства
- Copper — акцент, не основной цвет
- Анимации тонкие (200-300ms), не flashy
- Whitespace = роскошь

### Что НЕ делать
- Emoji в интерфейсе
- border-radius > 0 (кроме pill и circle)
- Яркие цвета (зелёный, красный, синий) — только brand palette
- Стоковые паттерны (gradient mesh, glassmorphism)
- Чекбоксы и радио-кнопки (выглядят дёшево) — вместо них кнопки-чипы

### Объяснять простым языком
Владелец — предприниматель, НЕ программист. Никаких "overlay", "z-index", "hover state". Вместо этого: "затемнение", "порядок слоёв", "при наведении мышкой".

## Уроки из опыта (ОБЯЗАТЕЛЬНО)

### Правило 1: Сначала изучи оригинал
ПЕРЕД созданием прототипа — открыть текущий сайт в Chrome DevTools, сделать скриншоты КАЖДОЙ секции. Составить таблицу "что есть на сайте". Не начинать прототип пока не изучен оригинал.

### Правило 2: Не удаляй — улучшай
Никогда не убирать элементы из оригинала. Только ДОБАВЛЯТЬ новое. Если кажется что что-то лишнее — спросить владельца. "Старое + новое" а не "новое вместо старого".

### Правило 3: Копируй стили из кода
Если элемент уже есть на сайте — grep компонент, скопируй Tailwind классы, переведи в CSS. Не изобретай новый дизайн для существующих элементов.

### Правило 4: Бэкап перед правками
Перед серией правок: `cp file.html file-vN-backup.html`. Всегда.

### Правило 5: Сохраняй уникальные дизайны в архив
Если создал уникальный дизайн и владелец выбрал оригинал — ВСЕГДА спросить "Сохранить этот вариант в архив?". Папка: `docs/prototypes/archive/`.

### Правило 6: Визуальное сравнение перед показом
ПЕРЕД показом прототипа — открыть оригинал рядом, сделать скриншоты, сравнить элемент за элементом. Составить таблицу: "есть на сайте / есть в прототипе / пропущено".

### Правило 7: Планируй 3-5 раундов feedback
Прототип — это диалог, не одноразовая доставка. Первая версия = 60%. Каждый раунд +10%.

### Правило 8: Валюта — $ по умолчанию
Доллары ($) везде. AED только в разделе "Билеты в парки". Не AED.

### Правило 9: Инфо-чипы — исключение
Инфо-чипы (~6 часов, Русский язык, и т.д.) — ОКРУГЛЫЕ (border-radius: 20px). Это единственное исключение из правила "border-radius: 0".

### Правило 10: Проверяй визуально после КАЖДОЙ правки CSS
Не говори "готово" пока не открыл в браузере и не сделал скриншот. Одна строка CSS может всё сломать.

### Правило 11: Владелец — перфекционист
Каждый пиксель имеет значение. "Почти как в оригинале" не подходит. Нужно точь-в-точь или лучше. Если стрелка чёрная вместо белой — это баг.

### Правило 12: Объясняй простым языком
Владелец НЕ программист и НЕ дизайнер. "Округлые края" а не "border-radius". "Стекольный эффект" а не "backdrop-filter". Всегда.
