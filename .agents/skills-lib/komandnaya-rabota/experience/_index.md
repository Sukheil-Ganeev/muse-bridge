## Критические уроки (топ-58)

> Читать при каждой активации скилла!

### 1. Максимум 8 скиллов/файлов на агента при чтении SKILL.md (EXP-CMD-001)
**Проблема:** Агенты с 15-16 скиллами падали "Prompt is too long" (3 из 6 агентов в Волне 0 проекта Skills Merge).
**Решение:** Разбивать на группы по 7-8 скиллов максимум. После разбивки -- 100% успех (0 падений из 9 агентов).
**Правило:** max_skills_per_agent = 8 для задач чтения/анализа SKILL.md.

### 2. Главное окно = только диспетчер, иначе потеря всей работы
**Проблема:** Если team-lead читает большие файлы или запускает тяжёлые операции в своём окне, контекст заполняется. Если главное окно заполнится раньше завершения тиммейтов -- ВСЯ РАБОТА ПРОПАДЁТ.
**Решение:** Главное окно НИКОГДА не читает файлы >5KB. Только создаёт задачи, назначает агентов, принимает краткие отчёты. Все тяжёлые операции -- через тиммейтов и субагентов.
**Влияние:** Предотвращение полной потери результатов многочасовой работы команды.

### 3. Mapper-агент в Волне 0 обязателен для merge/migration проектов (EXP-CMD-003)
**Проблема:** Без детального mapping'а merge-агенты не знают что сохранить, что дублируется, что нельзя потерять.
**Решение:** Mapper создаёт MERGE_MAPPING.md с планом для каждого merge: секции, дубли, чеклист "НЕЛЬЗЯ потерять" с конкретными фактами/числами. В Skills Merge: 6/6 merge-агентов получили точные инструкции = 100% успех, 0 retry.
**Влияние:** Гарантия сохранения контента при merge/migration операциях.

### 4. Бэкапы ПЕРЕД merge операциями, не после (EXP-CMD-002)
**Проблема:** Merge-агенты модифицируют целевые SKILL.md без предварительного бэкапа.
**Решение:** Pre-flight Check: "Создать бэкап всех целевых файлов перед merge". Формат: `_backups/{skill-name}_SKILL_{date}.md`.
**Влияние:** Страховка от потери данных при merge операциях.

### 5. Задачи и зависимости создавать ВСЕ СРАЗУ до запуска агентов
**Проблема:** Если создавать задачи по ходу работы, возникают гонки: агент стартует раньше, чем готовы данные от другого агента.
**Решение:** Создать ВСЕ задачи с зависимостями (addBlockedBy) ДО запуска первого агента. Каждый агент получает: что делать, куда сохранять, в каком формате, от кого зависит.
**Влияние:** Нет конфликтов, нет простоев, чёткий порядок выполнения.

### 6. DEPRECATED маркер лучше немедленного удаления (EXP-CMD-004)
**Проблема:** После merge искушение сразу удалить исходные скиллы, но если merge оказался неполным -- данные потеряны.
**Решение:** Вместо удаления -- DEPRECATED маркер в YAML description + blockquote в начале файла. Удаление -- отдельной задачей ПОСЛЕ верификации (Волна 4).
**Влияние:** Оригинальный контент сохранён как страховка до подтверждённой верификации.

### 7. При сбое -- ДИАГНОСТИКА, а не слепой перезапуск
**Проблема:** Team lead 3 раза перезапускал тиммейтов без анализа причины, потратив 30%+ контекста.
**Решение:** После ПЕРВОГО сбоя -- СТОП. Диагностика причины (ls файлов, проверка логов). Смена подхода (тиммейт -> субагент, больше файлов -> меньше файлов). НИКОГДА не повторять одно действие 3 раза.
**Влияние:** Экономия контекста и времени на бесполезные повторы.

### 8. Чеклист из mapping = 100% сохранение контента (EXP-CMD-006)
**Проблема:** При merge контент теряется -- агент "забывает" важные факты, числа, таблицы.
**Решение:** Каждый merge-агент получает конкретный чеклист фактов/чисел из mapping. Пример: "6 AED счетов: NBD Gulnaz, Mashreq Gulnaz..." -- агент верифицирует каждый пункт.
**Результат:** 18/18 (CV), 14/14 (YaDisk), все чеклисты (Bank, Formatting, Meta) -- 100% compliance.

### 9. Верификатор окупается ВСЕГДА -- даже при малом числе файлов
**Проблема:** Искушение пропустить верификацию на "простых" проектах (локальные данные, понятный формат).
**Решение:** В bot-migration (26 файлов) верификатор нашёл 4 критических бага (цены без AED, отсутствие условий отмены) + 3 некритических = 15% файлов с ошибками. Без верификации в продакшн попали бы некорректные данные.
**Влияние:** 15% ошибок -- стабильная метрика. Верификатор окупается при ЛЮБОМ количестве файлов.

### 10. Лимит 5000 слов при merge -- следить! (EXP-CMD-009)
**Проблема:** При объединении 2+ скиллов легко превысить лимит SKILL.md.
**Решение:** Mapper должен оценить размер результата и предложить вынос в references/ если >4500 слов. Пример: форматирование-турпродуктов (4893 слов) -- модульная система вынесена в references/modules.md.
**Влияние:** Соблюдение стандарта скиллов без потери контента.

### 11. Дедупликация = главный источник сокращения при рефакторинге скиллов (EXP-CMD-013)
**Проблема:** SKILL.md содержит полные копии контента, уже лежащего в references/ (промпты, пресеты, FAQ, примеры кода).
**Решение:** СНАЧАЛА проверяй existing references ПЕРЕД переносом нового контента. Удали дубликаты из SKILL.md, оставив ссылки на references/. Пример: фото-редактор-промты 11,981 -> 2,700 слов; vercel-деплой 7,708 -> 2,841 слов -- без потери данных.
**Влияние:** Экономия 60-80% объёма SKILL.md при рефакторинге, нулевые потери контента.

### 12. 1 скилл = 1 агент даже для лёгких скиллов (EXP-CMD-014)
**Проблема:** Объединение 2 лёгких скиллов (5500-6000 слов) в одного агента приводит к сбоям -- агент не справляется или выдаёт частичный результат.
**Решение:** Строгое правило 1:1 -- каждый скилл получает отдельного агента. Партия 2 (7 агентов на 7 скиллов): 7/7 успех, 0 сбоев. Партия 1 (6 агентов на 8 скиллов): 6/8 -- 2 агента упали на тяжёлых парах.
**Влияние:** 0 retry = экономия в итоге. Запас контекста важнее экономии на количестве агентов.

### 13. Haiku для микрофиксов (EXP-CMD-015)
**Проблема:** Для тривиальных правок (удалить 2 слова, исправить ссылку) запуск полного агента -- перерасход ресурсов.
**Решение:** Использовать model: "haiku" для микрофиксов. Пример: html-css 5002 -> 5000 слов за 30 сек, 104K токенов (vs 150K+ для полного агента).
**Влияние:** Экономия 30-50% токенов на тривиальных правках. Подходит для: удаление слов, исправление ссылок, мелкие правки текста.

### 14. Промты агентов в отдельном файле + предварительный анализ (EXP-CMD-016)
**Проблема:** Team lead тратит контекст, передавая промпты каждому агенту из главного окна. При 9 агентах -- значительный расход.
**Решение:** ПРОМТЫ_АГЕНТОВ.md -- файл с промптами для всех агентов. Каждый агент читает СВОЙ промпт сам. Плюс 3 файла предварительного анализа (analysis-*.md) дают полный контекст без исследования. В проекте Docker-справочник: 9 агентов, 3 фазы, 3 Quality Gates, 0 сбоев, 0 retry.
**Влияние:** Главное окно остаётся чистым, агенты автономны, паттерн подтверждён на 50+ файлах ~200KB контента.

### 15. DAG-оркестрация: презентации блокируются СВОИМ документом, не всеми (EXP-CMD-017)
**Проблема:** Последовательное выполнение (все исследования → все сравнения → все презентации) тратит ~30% лишнего времени. Презентация по ОАЭ не зависит от исследования России.
**Решение:** DAG-зависимости: исследования параллельно, сравнение блокировано обоими, презентации блокированы ТОЛЬКО своим документом. Brainstorm → AskUser → Plan → Team + Tasks с DAG.
**Влияние:** Экономия ~30% времени. Подтверждено: Credit Cards Research (7 агентов, 3 MD + 3 PDF, 0 retry).

### 16. Презентационные агенты -- детальный промпт критичен (EXP-CMD-018)
**Проблема:** Без детального промпта агент выбирает случайные цвета, использует неподдерживаемые CSS (animation, backdrop-filter, vh/vw), PDF конвертация падает.
**Решение:** Промпт ОБЯЗАТЕЛЬНО содержит: (1) полный CSS :root с палитрой, (2) структуру каждого слайда, (3) запрещённые CSS-свойства для PDF, (4) zero-dependency (системные шрифты, inline SVG), (5) Playwright скрипт конвертации, (6) пути сохранения HTML + PDF.
**Влияние:** 3 презентации с единой дизайн-системой, 0 ошибок конвертации. Серия: общие компоненты + уникальные палитры.

### 17. Shutdown по gate-правилу -- не забывать! (EXP-CMD-019)
**Проблема:** idle агенты занимают ресурсы (API лимиты). Team lead путает idle_notification с ошибкой.
**Решение:** shutdown_request сразу после выполнения задачи. idle_notification -- нормальное поведение, ИГНОРИРОВАТЬ. TeamDelete только после ВСЕХ агентов.
**Влияние:** Освобождение ресурсов по мере завершения задач. Контекст диспетчера не засорён.

### 18. Исследовательские проекты НЕ требуют верификации (EXP-CMD-013)
**Дата:** 2026-02-18 | **Категория:** pattern | **Severity:** medium
**Теги:** исследование, без-верификации, синтез, простые-презентации
**Суть:** Исследовательские проекты (не справочники) пропускают Волну 2 верификации. 8 агентов: 5 исследователей (параллельно) → 1 синтезатор → 2 презентационных. Синтезатор работает если файлы < 700 строк каждый. HTML-билдер получает CSS-систему в промпте (не нужен отдельный architect). Финализатор -- лёгкая задача (slideshow + PDF). Подтверждено: AI Companies Engineering Research, 574K токенов, 0 итераций.

### 19. Исследовательские агенты = general-purpose с детальной структурой (EXP-CMD-020)
**Проблема:** Без детальной структуры агент пишет "обзорную статью" вместо справочника. Без указания аудитории -- поверхностный текст.
**Решение:** Тип: general-purpose (WebSearch + Write). Промпт: детальная структура (все разделы), язык, объём (~3000 слов), формат (MD с таблицами), специфика аудитории. 1 агент = 1 тема.
**Влияние:** Структурированные справочники с таблицами и практическими рекомендациями.

### 19. Оптимальный размер команды: N_тем + N_перекрёстных + N_презентаций + 1 lead (EXP-CMD-021)
**Проблема:** Слишком мало агентов = последовательное выполнение. Слишком много = расход API и сложность координации.
**Решение:** Формула: N_тем (по 1 исследователю) + N_перекрёстных (сравнения) + N_презентаций (по 1 на каждую) + 1 lead (ТОЛЬКО диспетчер). Для Credit Cards: 2+1+3+1=7.
**Влияние:** 0 перезагрузок, контекст lead не переполнился, все агенты завершили работу.

### 20. DAG-паттерн подтверждён как воспроизводимый стандарт (EXP-CMD-022)
**Проблема:** DAG-паттерн (EXP-CMD-017) применён впервые в Credit Cards. Нужно было подтвердить воспроизводимость.
**Решение:** Тот же DAG без модификаций применён второй раз (Debit Cards): 7 агентов, параллельные фазы, зависимости. 0 retry в обоих проектах, одинаковое время выполнения.
**Влияние:** Паттерн подтверждён на 2/2 проектах. Статус: **стабильный стандарт** для проектов "исследование + сравнение + презентации".

### 21. Размер PDF -- индикатор потери визуальных элементов (EXP-CMD-022)
**Проблема:** PDF размеры сильно различались при одинаковом количестве слайдов (14): от 894 KB до 5.6 MB. Comparison debit (894 KB) подозрительно мал.
**Решение:** Корреляция: больше glow/blur элементов = больше PDF. ПРАВИЛО: < 1 MB для 14 слайдов с glow = вероятно что-то потерялось при конвертации. Ожидаемый диапазон: 1.5-6 MB.
**Влияние:** Раннее обнаружение потери визуальных элементов при HTML→PDF конвертации.

### 22. Зеркальные проекты -- шаблонизация промптов ускоряет в 3x (EXP-CMD-022)
**Проблема:** Первый проект серии требует полного проектирования промптов с нуля (~15 мин). Повторять это для каждого проекта -- потеря времени.
**Решение:** Копировать промпт предыдущего агента, менять ТОЛЬКО: (1) тему, (2) палитру CSS :root, (3) специфичные разделы. НЕ менять: структуру слайдов, запреты CSS, Playwright, DAG-зависимости, формулу команды.
**Влияние:** Второй проект (Debit Cards) запустился в 3x быстрее первого (Credit Cards). Время проектирования: ~15 мин -> ~5 мин.

### 23. Batch-улучшение файлов: 1 Explore + N параллельных (EXP-CMD-023)
**Проблема:** 3 HTML-презентации (russia, uae, comparison) нуждались в одновременном улучшении дизайна.
**Решение:** 1 Explore-агент для диагностики всех файлов -> 3 general-purpose агента параллельно (по 1 файлу на агента). Обычные субагенты (без team_name).
**Влияние:** 100% успех, 0 retry, все 3 файла обновлены синхронно. Подтверждённый стандарт (5-й проект подряд с обычными субагентами).

### 24. Итеративные правки тратят контекст -- точнее с первого раза (EXP-CMD-024)
**Проблема:** Добавили premium glow -> пользователь: "много свечений" -> убрали ВСЁ включая glassmorphism -> пользователь: "верни glass" -> 3 итерации x 3 файла = 9 агентов впустую.
**Решение:** ТОЧНЕЕ с первого раза. Спрашивай пользователя ДО агрессивных изменений. При запросе "убери X" -- убирай ТОЛЬКО X, не трогая связанные эффекты (glass != glow).
**Влияние:** Экономия ~9 агентов за сессию. Правило: glass != glow, отступы != контент, декор != структура.

### 25. CSS каскад через !important -- накопление мусора после 3+ итераций (EXP-CMD-025)
**Проблема:** После 5+ итераций CSS правок файл вырос с 70KB до 115KB (+65%). Каждая правка добавляла CSS в конец style с !important перезаписью.
**Решение:** После 3 итераций -- пересборка CSS (удалить дубликаты, объединить, убрать !important каскады). Аналог EXP-064 (пересборка > патчинг).
**Влияние:** Контроль размера файлов. Предотвращение CSS-спагетти и непредсказуемых побочных эффектов.

### 26. Диагностика ПЕРЕД каждой волной правок -- Explore-агент обязателен (EXP-CMD-026)
**Проблема:** Без предварительного аудита каждый агент "на глаз" оценивает проблемы -> несогласованный результат.
**Решение:** Explore-агент для design-audit (6 критериев: карточки, декоры, типографика, таблицы, уровень, специфика). Аудит выявил: russia 6/10, uae 6.5/10, comparison 7.5/10 -- точные данные для промптов каждого агента.
**Влияние:** Согласованные промпты на основе объективной диагностики. Каждый агент знает текущий уровень СВОЕГО файла.

### 27. transform: scale() -> zoom для fixed элементов (EXP-CMD-023)
**Проблема:** `document.body.style.transform = 'scale(x)'` создаёт новый containing block, ломая ВСЕ `position: fixed` элементы (TOC overlay, nav bar). TOC overlay получал height: 15120px вместо viewport.
**Решение:** `document.body.style.zoom = x` -- масштабирует контент БЕЗ поломки fixed positioning. Это было в EXP-094 (декоры), но повторилось -- ВСЕГДА проверять!
**Влияние:** Критично для всех HTML-презентаций с навигацией и overlay. Повторяющаяся ошибка -- нужно проверять на каждом проекте.

### 28. e.code вместо e.key для русской раскладки (EXP-CMD-023)
**Проблема:** `e.key === 'T'` в русской раскладке возвращает 'Е' (кириллица), `e.key === 'F'` возвращает 'А'. Горячие клавиши не работают в RU раскладке.
**Решение:** `e.code === 'KeyT'` -- физическая клавиша, работает в ЛЮБОЙ раскладке. Стрелки, Escape, Home, End можно оставить через e.key (они одинаковые).
**Влияние:** Все keyboard shortcuts работают для русскоязычной аудитории. Обязательное правило для всех интерактивных HTML-презентаций.

### 29. Кодовый проект: Wave A/B/C/D паттерн вместо 5-волновой архитектуры (EXP-CMD-029)
**Проблема:** 5-волновая архитектура (research → verification → writing → presentation → QA) избыточна для кодовых проектов. Не нужны: research, critic, advocate, technical-writer, presentation.
**Решение:** Паттерн волн для кода: Wave A (параллельные impl-агенты, каждый создаёт свой файл) → Wave B (зависимые impl-агенты, ждут Wave A) → Wave C (wiring-агент + test-агент параллельно) → Wave D (verification / pytest). Тестовый агент = верификатор (отдельный verification-агент не нужен). ContentFactory: 16 агентов, 22 файла, 188 тестов, 0 сбоев.
**Влияние:** Экономия 3-5 агентов на проект. Подтверждено в ContentFactory Волны 2-3 (2 волны по 7-9 агентов).

### 30. Один файл = один агент (конфликт при параллельном редактировании) (EXP-CMD-030)
**Проблема:** Волна 2 ContentFactory: задачи Photo→Text и AI Generator обе модифицировали `ai_adapter.py`. Два агента параллельно редактируют один файл → конфликт.
**Решение:** Если 2 задачи модифицируют ОДИН файл → объединить в одного агента. Альтернатива: wiring-агент отдельно (не давать impl-агентам модифицировать main.py / __init__.py). Один wiring-агент читает ВСЕ новые модули и подключает разом.
**Влияние:** Нет конфликтов при параллельном выполнении, единый стиль wiring, проверка совместимости.

### 31. Naming collision в БД -- проверять существующие таблицы (EXP-CMD-031)
**Проблема:** Волна 3 ContentFactory: `metrics.py` обнаружил существующую таблицу `metrics` → назвал свою `publication_metrics`. `ab_testing.py` обнаружил `ab_tests` → назвал `ab_tests_v2`.
**Решение:** В промпте агенту УКАЗЫВАЙ: "прочитай database.py и проверь существующие таблицы ПЕРЕД созданием своих". Агент должен выбрать уникальное имя, не коллидирующее с существующими.

### Паттерн: Code Project Wave Pipeline

Для кодовых проектов (боты, сервисы, библиотеки):

```
Wave A: Параллельные impl-агенты
  ├── Каждый агент создаёт СВОЙ файл (1 файл = 1 агент)
  ├── Если 2 задачи → 1 файл → объединить в 1 агента
  └── Impl НЕ трогают main.py / __init__.py

Wave B: Зависимые impl-агенты (ждут Wave A)
  └── Задачи, зависящие от модулей из Wave A

Wave C: Параллельно
  ├── Wiring-агент: подключает ВСЕ новые модули в main.py + __init__.py
  └── Test-агент: пишет тесты для всех новых модулей

Wave D: Verification
  └── Test-агент сам запускает pytest (или отдельный если >7 файлов)
```

**Ключевые правила:**
1. НЕ нужны: research, critic, advocate, technical-writer, presentation
2. Один файл = один агент (нет конфликтов при параллельном выполнении)
3. Wiring-агент отдельно от impl-агентов
4. Тест-агент = верификатор (pytest = verification)
5. Graceful degradation в промпте каждого агента
6. "Прочитай database.py перед созданием таблиц" в промпте

**Оптимальное соотношение:** N impl (Wave A) + M impl (Wave B) + 1 wiring + 1 test = N+M+2 агентов.
