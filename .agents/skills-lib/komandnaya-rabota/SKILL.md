# Командная работа

Скилл для координации многоагентных команд в Claude Code.
Используй когда проект требует 3+ параллельных агентов с зависимостями.

## Ключевой принцип

Главное окно = ДИСПЕТЧЕР. Никогда не выполняй тяжёлые операции
в главном окне. Делегируй тиммейтам. Если контекст главного окна
заполнится раньше завершения тиммейтов -- ВСЯ РАБОТА ПРОПАДЁТ.

---

## Когда использовать

ИСПОЛЬЗУЙ когда:
- Проект требует 3+ параллельных агентов
- Есть зависимости между задачами (Волна 2 ждёт Волну 1)
- Нужна верификация результатов (critic/advocate)
- Проект создаёт множество файлов

НЕ ИСПОЛЬЗУЙ когда:
- Задача решается 1-2 агентами -- используй Task tool напрямую
- Нет зависимостей между задачами -- используй dispatching-parallel-agents
- Одноразовая простая задача

## Паттерн волн -- принцип

Любой командный проект разбивается на ВОЛНЫ -- группы задач
с общими зависимостями.

ВОЛНА = группа задач, которые:
- Могут выполняться ПАРАЛЛЕЛЬНО внутри волны
- Зависят от ЗАВЕРШЕНИЯ предыдущей волны
- Производят АРТЕФАКТЫ для следующей волны

### Правила волн

1. ВНУТРИ волны -- максимальная параллельность
2. МЕЖДУ волнами -- строгие зависимости (blockedBy)
3. ВОЛНА ВЕРИФИКАЦИИ -- обязательна (интернет содержит ошибки)
4. Поздние волны могут стартовать ПАРАЛЛЕЛЬНО если зависят
   от одной и той же предыдущей волны
5. Shutdown агентов после прохождения Quality Gate --
   не сразу после завершения, а после gate (агенты могут понадобиться
   для уточнений между завершением волны и проверкой)

### Типичная последовательность волн

| Волна | Задача | Типичные роли |
|-------|--------|---------------|
| 0 (опц.) | Pre-research | 1-2 легковесных агента |
| 1 | Исследование | architect + researchers (параллельно) |
| 2 | Верификация | critic + advocate |
| 3 | Создание | technical-writer |
| 4 | Презентация | architect + design + html + finalizer |
| 5 | Улучшения | qa + diagrams + templates + interactive |

> Подробнее: references/workflow-diagrams.md (flowchart, dot-граф, визуализации)

### Pre-research (Волна 0)

Перед Волной 1 -- запусти 1-2 агента для сбора контекста.
Это даёт architect'у и team-lead'у лучшую основу для планирования.

Когда применять:
- Тема новая / незнакомая
- Есть существующие примеры (другие скиллы, справочники)
- Нужно понять масштаб задачи ДО распределения по агентам

Протокол:
1. Агент анализа примеров -- читает существующие справочники, извлекает структуру
2. Агент исследования темы -- WebSearch, определение количества разделов
3. Оба запускаются ПАРАЛЛЕЛЬНО (run_in_background: true)
4. Результаты -> {PROJECT_PATH}/_research/pre-research/
5. Architect получает эти файлы как INPUT для structure-plan.md

Правила:
- НЕ заменяет Волну 1 -- это ДОПОЛНЕНИЕ
- Если pre-research не дал результатов -- не задерживай, запускай Волну 1
- Timeout для TaskOutput: 300 секунд

**ОБЯЗАТЕЛЬНО:** При создании презентации загрузи скилл `pdf-презентации`
для html-css-developer и presentation-finalizer. Скилл содержит критические
CSS правила для PDF-конвертации и 68 уроков из предыдущих проектов.

### Handoff между волнами

Каждый промпт следующей волны ДОЛЖЕН содержать точные пути к файлам.

Шаблон:
```
ВОЛНА {N} -> ВОЛНА {N+1}:
  Передать:
    paths: [список путей к файлам]
    format: "Прочитай файлы: {paths}"
    critical: "ИСПОЛЬЗУЙ ИСПРАВЛЕННЫЕ данные из advocate, НЕ исходные"
```

- ХОРОШО: "Прочитай 3 конкретных файла: [путь1], [путь2], [путь3]"
- ПЛОХО: "Прочитай все файлы проекта" -- слишком широко, агент потеряется

> Подробнее: references/handoff-protocol.md (конкретные handoff'ы между волнами)

### Quality Gates

Между волнами -- обязательная точка контроля. Лидер НЕ запускает
следующую волну пока не проверит gate.

| Gate | Между | Что проверить | Критерий |
|------|-------|--------------|---------|
| G1 | Волна 1 -> 2 | Все файлы на месте | 100% файлов, >1KB каждый |
| G2 | Волна 2 -> 3 | Критические ошибки | 0 неразрешённых КРИТИЧЕСКИХ |
| G3 | Волна 3 -> 4,5 | Основные файлы | SKILL.md + все reference |

Если gate НЕ пройден:
1. Определи что не так (какой агент не доставил)
2. Запусти fix-агента для устранения
3. Повтори gate
4. Только после прохождения -- следующая волна

НЕ читай файлы сам. Запусти Explore-агента:
"Проверь что файлы [список путей] существуют и содержат данные."

> Подробнее: references/troubleshooting.md (pre-flight checklist, recovery)

## Тиммейты vs Субагенты -- когда что использовать

### Критическое правило

Тиммейты (Task с team_name) получают задачу через mailbox-систему.
Обычные субагенты (Task без team_name) получают промпт НАПРЯМУЮ при запуске.

| Параметр | Тиммейты (team_name) | Субагенты (без team_name) |
|----------|---------------------|--------------------------|
| Получение задачи | Через mailbox (НЕНАДЕЖНО) | Напрямую при запуске (НАДЕЖНО) |
| Общение между собой | Да (SendMessage) | Нет |
| Shutdown | СЛОЖНО, могут продолжать idle | Завершаются чисто |
| Idle-уведомления | Засоряют контекст лидера | Не засоряют |
| Лучше для | Координация МЕЖДУ агентами | Независимые задачи чтения/записи |

### Правило выбора

- По умолчанию: ОБЫЧНЫЕ СУБАГЕНТЫ (Task без team_name)
- Тиммейты: ТОЛЬКО когда агенты ДОЛЖНЫ общаться между собой
- Если тиммейт ушёл в idle без работы -- НЕ перезапускай,
  переключись на обычный субагент

### Подтверждённый опыт (5 проектов)

- **Битрикс24 (2026-02):** 18+ задач обычными субагентами -- 100% успех,
  0 mailbox-проблем. Параллельный запуск 7 исследователей
  (run_in_background: true). TaskOutput timeout 300-600 секунд --
  надёжнее стандартных 120 секунд для тяжёлых задач.
- **PuzzleBot (2026-02):** 4 тиммейта = 0 файлов, субагенты = 100%.
- **Gaming Guides (2026-02):** 7 тиммейтов = 0 файлов,
  фоновые агенты = 7/7.
- **MLCR Investor Bot (2026-02):** 4 фазы, 10+ агентов, 54 файла.
  Фазовая архитектура (A+C параллельно -> B -> D -> E+QA).
  Урок: при параллельных агентах на связанных модулях определять
  интерфейсы ЗАРАНЕЕ (имена функций, классов, enum).
  Без этого: 5 критических багов в Фазе 3.
  QA-агент как фиксер экономит round-trip.
- **Вывод:** Обычные субагенты -- проверенный стандарт
  для 5 из 5 проектов.

## Защита контекста главного окна

### КРИТИЧЕСКОЕ ПРАВИЛО

Главное окно = ДИСПЕТЧЕР. Оно ТОЛЬКО:
- Создаёт задачи (TaskCreate)
- Назначает задачи (TaskUpdate)
- Запускает агентов (Task tool)
- Принимает краткие отчёты (SendMessage)
- Останавливает агентов (shutdown_request)

### Что НЕЛЬЗЯ делать в главном окне

| Действие | Почему нежелательно | Что делать вместо |
|----------|---------------------|-------------------|
| Читать файлы >5KB систематически | Заполняет контекст | Делегируй агенту (одноразово до 10KB -- ОК) |
| Запускать WebSearch | Результаты огромные | Делегируй агенту |
| Писать файлы | Контент занимает место | Делегируй агенту |
| Длинные промпты | Каждый символ на счету | Ссылайся на файлы |

### Базовые лимиты контекста

- Каждый тиммейт при запуске: ~2-3K токенов
- Каждое сообщение от тиммейта: ~500-1000 токенов
- Каждый TaskCreate/TaskUpdate: ~200 токенов
- Бюджет главного окна: ~150K токенов
- Максимум тиммейтов: 18 базовый + 2-3 fix = до 21
- Если больше -- разделяй на сессии

> Подробнее: references/context-budgets.md (полные формулы, расчёты)

### Если контекст заканчивается

1. НЕМЕДЛЕННО: shutdown всех idle тиммейтов
2. Проверь TaskList -- какие задачи завершены
3. Сгенерируй файл продолжения, сохрани состояние
4. Закрой сессию, открой новую с файлом продолжения

> Подробнее: references/продолжение-шаблон.md (шаблон, checkpoint snapshots)

## Управление командой -- краткий справочник

### Жизненный цикл

```
TeamCreate -> TaskCreate (все задачи) -> Task (запуск агентов)
-> TaskList (мониторинг) -> Quality Gate -> Shutdown -> TeamDelete
```

### Создание команды и задач

1. TeamCreate -> team_name: "название-проекта"
2. Создай задачи Волны 1 + каркас задач Волн 2-5 ПЕРЕД запуском
3. TaskUpdate addBlockedBy для зависимостей
4. Уточни задачи Волн 2-5 после structure-plan.md от architect

### Запуск агентов

Task tool с параметрами:
- subagent_type: "general-purpose" (WebSearch, файлы) или "Explore" (чтение/анализ)
- mode: "bypassPermissions"
- run_in_background: true
- name: "имя-роли"

### Мониторинг и завершение

- TaskList -- статус всех задач
- Idle notifications -- автоматические, не реагируй если не нужно
- SendMessage type: "shutdown_request", recipient: "имя" -- после gate
- НЕ ДЕРЖИ завершённых агентов -- они забивают ресурсы
- После всех волн: проверь TaskList -> shutdown всех -> TeamDelete

> Подробнее: references/команды-api.md (полный API: TeamCreate, TaskCreate,
> TaskUpdate, SendMessage, activeForm и др.)

## Восстановление при сбоях -- краткий справочник

### Агент упал / не завершил задачу

1. Проверь выходной файл: существует? полный?
   (делегируй Explore-агенту, НЕ читай сам)
2. Файл есть но неполный -> новый агент: "Продолжи. Готовая часть: [путь]"
3. Файла нет -> запусти задачу заново
4. TaskUpdate: переназначь задачу новому агенту

### TaskOutput пуст -- это НЕ сбой

TaskOutput может вернуть пустой результат, хотя агент реально
завершил работу. Проверь целевой файл напрямую через Explore-агента.
Если файл на месте -- задача выполнена, продолжай.

### Протокол диагностики (ПЕРЕД перезапуском)

НЕ ПЕРЕЗАПУСКАЙ СРАЗУ. Выполни диагностику:
1. Файл создан? (ls через Bash, НЕ читай содержимое)
2. Файл пуст -> mailbox miss -> переключись на субагент
3. Файла нет -> агент не стартовал -> перезапуск
4. "Prompt is too long" -> раздели на 2 агента

НИКОГДА не повторяй одно и то же действие больше 1 раза без диагностики.
Retry budget: 1 попытка того же метода, затем ОБЯЗАТЕЛЬНО смена подхода.

### Некачественный результат

1. НЕ фикси сам в главном окне
2. Запусти fix-агента: "Прочитай [файл]. Проблемы: [список]. Исправь."
3. Fix-агент сохраняет исправленную версию

> Подробнее: references/troubleshooting.md (retry budget, DoD, recovery)

## Размер команды и слияние ролей

### Быстрый выбор

| Масштаб | Агентов | Состав |
|---------|---------|--------|
| Малый (3-5) | 5-6 | 2-3 исследователя + 1 verifier + 1 writer |
| Средний (8-12) | 10-12 | 4-6 исследователей + critic + advocate + 1-2 writer + QA |
| Полный (18+) | 18-24 | 7 исследователей + 2 верификатора + writer + 4 презентация + 4 улучшения |

### Совместимые роли (можно объединять)

| Роль A + Роль B | = Объединённая | Когда |
|-----------------|----------------|-------|
| critic + advocate | verifier | < 10 разделов |
| qa + template-creator | qa-templates | Средний проект |
| design + html-css | presentation-builder | Подтверждено (Битрикс24) |
| finalizer + interactive | presentation-polisher | Подтверждено (Битрикс24) |

### Несовместимые роли (НЕЛЬЗЯ объединять)

| Роль A + Роль B | Почему |
|-----------------|--------|
| researcher + critic (свой файл) | Нельзя проверять СВОЙ файл |
| architect + researcher | Architect видит общую картину |
| writer + researcher | Writer работает с ПРОВЕРЕННЫМИ данными |

> Подробнее: references/team-calculator.md (формула, входные данные)
> Подробнее: references/team-configs.md (конфигурации, контент-миграция,

## Приоритеты при нехватке ресурсов

P0 -- НЕЛЬЗЯ ПРОПУСТИТЬ:
- Волна 1 (исследование) -- без данных нет проекта
- Волна 2 (верификация) -- без проверки данные ненадёжны
- Волна 3 (написание) -- это основной результат

P1 -- ПОТЕРЯ КАЧЕСТВА:
- QA-тестер, diagram-designer, quality gates

P2 -- МОЖНО СДЕЛАТЬ ПОЗЖЕ:
- Презентация, templates, interactive

### MVP команда (5-6 агентов)

| Этап | Агентов | Кто |
|------|---------|-----|
| Исследование | 3-4 | researchers |
| Верификация | 1 | critic-advocate (совмещённая) |
| Написание | 1 | technical-writer |

MVP даёт: скилл + проектная папка. Презентацию и QA -- в следующей сессии.

### Решение по ходу

- После Волны 2, контекст > 60%: запусти writer -> файл продолжения
- После Волны 3, контекст > 60%: файл продолжения -> новая сессия

> Подробнее: references/resource-priorities.md (конкуренция за API)

## Золотые правила

1. **Главное окно = диспетчер.** Не читай файлы >5KB без необходимости.
   Одноразовая проверка до 10KB -- допустима.
   Если контекст кончится -- ВСЯ РАБОТА ПРОПАДЁТ.

2. **Задачи Волны 1 -- СРАЗУ.** Задачи Волн 2-5 -- уточнить
   после structure-plan.md от architect.

3. **Верификация ОБЯЗАТЕЛЬНА.** < 6 файлов = 1 verifier,
   >= 6 = critic + advocate. В первом проекте нашли 7 критических ошибок.

4. **Shutdown после Quality Gate.** Между завершением волны и gate
   агенты могут понадобиться для уточнений.

5. **Детальные промпты.** Каждый агент должен знать ТОЧНО:
   что делать, куда сохранить, какой формат, output template.

6. **run_in_background: true + bypassPermissions.** Все агенты в фоне,
   без запросов разрешения. Не жди завершения -- координируй.

7. **При сбое -- ДИАГНОСТИКА, не повтор.** После первого сбоя -- СТОП.
   Выясни причину. Retry budget: 1 попытка того же метода, затем смена.
   Каждый перезапуск тратит контекст главного окна.

8. **WebSearch в каждого исследователя.** Без актуальных данных
   результат устаревает. Используй subagent_type: "general-purpose".

9. **Интерфейс-контракт для связанных модулей.** Когда 2+ агента
   работают над связанными модулями -- определи имена функций, классов,
   enum ЗАРАНЕЕ и передай ВСЕМ. Без этого: конфликты (Investor Bot: 5 багов).

10. **QA-агент = фиксер.** QA должен не только находить баги,
    но и ФИКСИТЬ. Это экономит round-trip.
    Используй general-purpose + bypassPermissions.

11. **Презентации -> скилл pdf-презентации.** Если в проекте
    есть HTML -> PDF, ОБЯЗАТЕЛЬНО загрузи скилл `pdf-презентации`.
    Без него презентации будут с артефактами.

## Антипаттерны

| Делать | Вместо этого |
|--------|--------------|
| Читать файлы в главном окне | Делегировать агенту |
| Запускать все 18 агентов разом | Волнами с зависимостями |
| Пропускать верификацию | Critic + advocate (>= 6 файлов), verifier (< 6) |
| Держать idle агентов | Shutdown после Quality Gate |
| Давать короткие промпты | Детальные с форматом и путями |
| Создавать задачи по ходу | Волна 1 -- сразу; Волны 2-5 -- уточнить после architect |
| Ждать агента синхронно | run_in_background: true |
| Перезапускать без диагностики | Остановиться, выяснить причину, сменить подход |
| Давать субагенту >5 больших файлов | Максимум 3-4 файла/раздела на агента |
| Параллельные агенты без контракта | Определить интерфейсы ЗАРАНЕЕ |
| QA только находит баги | QA-агент = фиксер (general-purpose) |
