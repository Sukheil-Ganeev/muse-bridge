# Командная работа: Справочники

Production-ready создание справочников по платформам, сервисам,
транспортным системам и другим темам. 18 тиммейтов, 5 волн,
от исследования до интерактивной презентации.

**REQUIRED:** Используй скилл `командная-работа` для базовых принципов
координации команд. Этот скилл НАСЛЕДУЕТ все универсальные принципы оттуда:
Quality Gates, Error Recovery, Retry Budget, Handoff-протокол, защита контекста,
управление командой, Pre-flight Check, калькулятор команды, метрики, антипаттерны.
Здесь -- ТОЛЬКО специфика справочников.

---

## Результаты проекта

Каждый проект справочника создаёт ТРИ артефакта:

1. **Скилл:** ~/.claude/skills/{name}/ (SKILL.md ~5000 слов + references/ + diagrams/)
2. **Проектная папка:** D:/Downloads/{NAME}_СПРАВОЧНИК/ (14 разделов + _research/ + _qa/)
3. **Презентация:** D:/Downloads/Skill_Presentations/{name}/ (50-60 слайдов, dark mode)

## Quick Start

### Подготовка (5 минут)

1. Определи {TOPIC} -- тема справочника
2. Определи {SECTIONS} -- 14 разделов (используй references/адаптация-разделов.md)
3. Определи {RESEARCHERS} -- 5-6 исследователей по разделам

### Запуск

4. TeamCreate -> team_name: "{topic}-справочник"
5. mkdir папки:
   - D:/Downloads/{TOPIC}_СПРАВОЧНИК/_research/
   - D:/Downloads/{TOPIC}_СПРАВОЧНИК/_qa/
   - D:/Downloads/Skill_Presentations/{topic}/
6. TaskCreate x 18 (все задачи, см. references/шаблоны-промптов.md)
7. TaskUpdate addBlockedBy (зависимости по волнам)
8. Запусти Волну 1 (7 агентов параллельно)
9. По завершении каждой волны -> shutdown -> следующая волна
10. После всех волн -> TeamDelete

#### Discovery Protocol

Если исследователь нашел важные данные, которые НЕ входят в его разделы:

1. Записать в КОНЕЦ своего файла в секции:
   ```
   ### ОБНАРУЖЕНО (вне моих разделов)
   - Что: {описание находки}
   - Почему важно: {объяснение}
   - Источник: {URL}
   - Рекомендуемый раздел: {если понимает куда}
   ```

2. В промпт КАЖДОГО исследователя добавить:
   "Если найдёшь данные, которые не относятся к твоим разделам --
   НЕ ВЫБРАСЫВАЙ. Запиши в секцию ОБНАРУЖЕНО в конце файла."

3. Critic в Волне 2 проверяет ВСЕ секции ОБНАРУЖЕНО:
   -> Определяет куда включить
   -> Помечает в critic-report.md

4. Technical-writer интегрирует находки в соответствующие разделы.

#### Стандартный шаблон вывода исследователя (Research Output Template)

Каждый исследователь ОБЯЗАН использовать этот каркас:

```
## {Название раздела}

### Обзор
{2-3 предложения: что это, для кого, почему важно}

### Основные данные
| Параметр | Значение | Источник (URL) |
|----------|----------|----------------|
| ...      | ...      | ...            |

### Детали
{СВОБОДНАЯ ФОРМА -- таблицы, списки, текст.
ВСЁ что нашёл и не поместилось в "Основные данные" -- сюда.
НЕ выбрасывай информацию. Лучше лишнее чем потерять.}

### Советы для туристов
- {совет 1}
- {совет 2}

### Источники
| # | Источник | Tier | URL |
|---|----------|------|-----|

### ОБНАРУЖЕНО (вне моих разделов)
{Находки не по моей теме -- см. Discovery protocol}
```

**Обязательные секции:** Обзор, Основные данные (таблица), Источники.
**Свободные секции:** Детали (формат на выбор), Советы, Обнаружено.

| 9 | advocate | Верифицирует спорные факты через WebSearch | critic-report.md | advocate-verification.md |

**ВОЛНА 2 ОБЯЗАТЕЛЬНА.** В проекте Taplink нашли 7 критических ошибок:
- Несуществующий REST API
- Путаница тарифов

- Несуществующее мобильное приложение
- Неправильное количество языков

- Фактические ошибки из поисковой выдачи

**Главный урок:** НИКОГДА не пропускать Волну 2. Интернет содержит
противоречивую информацию. Critic + Advocate -- обязательный этап.

#### Стратегия critic'а (поэтапное чтение -- Context Overflow Protection)

Critic НЕ загружает все 7 файлов одновременно.

**Этап 1:** Прочитай structure-plan.md
  -> Понять архитектуру разделов и кто что исследовал

**Этап 2:** Читай файлы ПОПАРНО по смежным темам:
  - research-1.md + research-2.md -> записать найденные проблемы в critic-report.md
  - research-3.md + research-4.md -> дописать в critic-report.md
  - research-5.md + research-6.md -> дописать в critic-report.md

**Этап 3:** Прочитай critic-report.md (свои заметки) + structure-plan.md
  -> Ищи системные проблемы (пересечения тем, пропущенные данные)
  -> Финализируй critic-report.md с оценками по скоринг-рубрике

**Ключевое:** ЗАПИСЫВАЙ проблемы СРАЗУ в файл (append), не держи в памяти.
В промпте critic'а указать:
"НЕ читай все файлы сразу. Читай попарно, записывай проблемы сразу в critic-report.md."

Critic оценивает каждый файл по скоринг-рубрике (см. references/скоринг-рубрика.md).

#### Протокол QA-tester'а

QA-tester записывает ВСЁ найденное в _qa/qa-report.md.

**Действия по типу ошибки:**

| Тип ошибки | Пример | Действие QA |
|------------|--------|-------------|
| Мелкая (формат) | Опечатка, сломанная таблица, пропущен заголовок | Исправить САМ в файле |
| Средняя (данные) | Неточная цифра, устаревший факт | Записать в qa-report -> лидер запустит fix-агента |
| Крупная (структура) | Пропущен целый раздел, дублирование | Записать в qa-report -> лидер запустит fix-агента |

**Что QA НЕ трогает:**
- presentation.html (там свой finalizer)
- diagrams/ (там diagram-designer)
- Файлы в _research/ (это архив, не редактировать)

**Формат qa-report.md:**

| # | Файл | Тип | Описание | Статус |
|---|------|-----|----------|--------|
| 1 | SKILL.md:45 | мелкая | Опечатка | исправлено |
| 2 | references/faq.md | средняя | Цена устарела | нужен fix-агент |

## Ранжирование источников

Каждый исследователь ОБЯЗАН приоритизировать источники:

**Tier 1 -- ДОВЕРЯЙ:** Официальные сайты платформы/сервиса
**Tier 2 -- ПРОВЕРЯЙ:** Крупные СМИ (Gulf News, TechCrunch, The Verge)
**Tier 3 -- ПЕРЕПРОВЕРЯЙ:** Блоги, форумы, Reddit, YouTube
**Tier 4 -- разделён:**
  - AI-сгенерированные статьи без ссылок -> ПОЛНЫЙ БАН
  - Данные >2 лет -> НЕ бан, а пометка [ДАННЫЕ {ГОД} -- ПРОВЕРИТЬ АКТУАЛЬНОСТЬ]
  - Исследователь решает: если тема стабильная (станции метро, адреса) -- данные 2022 ОК

**ПРАВИЛО:** Каждый факт = Tier 1 или Tier 2 источник.
Tier 3 допустим ТОЛЬКО если Tier 1-2 не найден -> пометить [ТРЕБУЕТ ПРОВЕРКИ].

В каждом промпте исследователя ОБЯЗАТЕЛЬНО:
"Приоритизируй официальные источники. Для каждого факта укажи источник.
Если источник -- блог/форум, пометь [ТРЕБУЕТ ПРОВЕРКИ]."

## Требования к презентации

### Обязательные (из опыта)

| Требование | Детали | Почему критично |

| Overlay fade | 150ms in + 150ms out для переключения тем | CSS transition = "лоскутный" эффект |

| < 250KB | Без внешних зависимостей | Быстрая загрузка |
| 50-60 слайдов | По всем 14 разделам | Полнота |
| Скилл pdf-презентации | REQUIRED для html-css-developer | 68 уроков, CSS для PDF, Apple fix |

### Hotkeys

| Клавиша | Действие |
|---------|----------|
| <- -> | Навигация |
| D | Dark/Light mode |
| T | Table of Contents |
| H | Help |
| F | Fullscreen |
| Ctrl+F | Поиск |

## Адаптация разделов (Config Library)

14 -- это шаблон, не догма. Для каждого проекта architect
определяет конкретные разделы. Рекомендуется 10-16, но architect
определяет реальное количество исходя из объёма темы.
8 полных разделов лучше чем 14 с водой. 18 плотных -- лучше
чем 14 с объединёнными темами.

Полные пресеты -- см. references/адаптация-разделов.md.

### 4 пресета проектов (краткий обзор)

| Пресет | Для чего | Примеры |
|--------|----------|---------|
| platform-guide | Справочник по платформе | Taplink, Salebot, Shopify, Tilda |
| messenger-guide | Справочник по мессенджеру | Telegram, WhatsApp, VK, Viber |
| transport-guide | Транспортная база | UAE Transport и аналогичные |
| bot-guide | Справочник по бот-платформе | PuzzleBot, Salebot bots, BotFather |

### Правила адаптации

1. Architect ВСЕГДА определяет разделы в Волне 1
2. Рекомендуется 10-16 разделов, но architect определяет реальное количество исходя из объёма темы
3. Каждый раздел = 3-5 файлов = 1 подпапка
4. Исследователи распределяются по 2-3 раздела каждый
5. Баланс: ни один раздел не должен быть "пустым"

### Использование пресета

1. Architect в Волне 1 ВЫБИРАЕТ пресет
2. Адаптирует названия разделов под конкретную тему
3. Распределяет исследователей (по 2-3 раздела на каждого)
4. Сохраняет в structure-plan.md

## Версионирование справочников

Справочники устаревают. Протокол обновления:

### Версии

| Версия | Когда | Команда | Что делать |
|--------|-------|---------|------------|
| v1.0 | Первая версия | Полная (18 агентов) | Полный цикл 5 волн |
| v1.x | Мелкие правки | 2-3 агента | researcher + writer |
| v2.0 | Крупное обновление | 10-12 агентов | Новые разделы, перепроверка |

### В SKILL.md справочника добавить

```
Version: 1.0
Created: {DATE}
Last updated: {DATE}
Next review: {DATE + 3 months}
```

### Протокол обновления v1.x (мелкие)

1. Запусти 1-2 researchers на устаревшие разделы
2. Запусти critic для проверки обновлений (1 агент, объединяет с advocate)
3. Запусти writer для интеграции изменений
4. НЕ нужна полная команда, НЕ нужна презентация

### Протокол обновления v2.0 (крупные)

1. Architect переопределяет разделы
2. 4-6 researchers на новые/изменённые разделы
3. Полная верификация (critic + advocate)
4. Writer интегрирует
5. Обновить презентацию (если есть)

### Триггер обновления

- Прошло 3+ месяца с last updated
- Платформа выпустила крупное обновление
- Пользователь нашёл устаревшие данные
- Появились новые разделы/функции

## Scoring Rubric для Critic

Полная рубрика -- см. references/скоринг-рубрика.md.

### Краткая версия

| Критерий | 0 (плохо) | 1 (норма) | 2 (отлично) |
|----------|-----------|-----------|-------------|
| Полнота | Пропущены ключевые данные | Основное есть, мелочи пропущены | Исчерпывающе, всё на месте |
| Точность | Фактические ошибки | Мелкие неточности | Всё верифицируемо верно |
| Источники | Нет ссылок на источники | Блоги, форумы (Tier 3) | Официальные сайты (Tier 1-2) |
| Формат | Нечитаемо, нет таблиц | Читаемо, базовые таблицы | Идеальные таблицы |
| Актуальность | Данные >2 лет | В целом актуально (1-2 года) | Свежие данные текущего года |

- Максимум: 10 баллов на файл
- ПОРОГ: если ЛЮБОЙ файл < 5 баллов -> вернуть на ДОРАБОТКУ (НЕ переписывание!)
- Critic указывает КОНКРЕТНО что исправить
- Fix-агент ДОПОЛНЯЕТ исходный файл, а не перезаписывает
- Уникальные данные из исходного файла СОХРАНИТЬ

### Формат в critic-report.md

| Файл | Полнота | Точность | Источники | Формат | Актуальность | ИТОГО | Статус |
|------|---------|----------|-----------|--------|-------------|-------|--------|
| research-1.md | 2 | 1 | 2 | 2 | 2 | 9/10 | OK |
| research-2.md | 1 | 0 | 1 | 1 | 1 | 4/10 | ДОРАБОТКА |

## Золотые правила справочников

Дополнительно к правилам из `командная-работа`:

1. **WebSearch в каждого исследователя.** Без актуальных данных
   справочник устаревает.

2. **Помечай [ТРЕБУЕТ ПРОВЕРКИ].** Лучше пометить, чем пропустить ошибку.

3. **Рекомендуется до 15KB на файл;** если больше -- разбить на логические
   части, НЕ обрезать контент.

4. **Не дублируй данные.** Каждый факт -- в одном файле. Остальные ссылаются.

5. **"ДАННЫЕ АКТУАЛЬНЫ НА: [дата]"** в начале каждого reference-файла.

6. **63/63 проверок QA.** Стремись к 100% pass rate.

7. **Fallback:** Если данные не найдены -> [НЕ НАЙДЕНО], не выдумывай.

8. **Один стиль.** Все таблицы, заголовки, форматирование -- единообразно.
