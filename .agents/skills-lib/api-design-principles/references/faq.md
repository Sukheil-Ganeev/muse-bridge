# FAQ — api-design-principles

## Q1: Когда выбирать REST, а когда GraphQL?
**REST** подходит для простых CRUD-операций, публичных API, кэшируемых ресурсов и микросервисов. **GraphQL** выигрывает при сложных связях между данными, мобильных клиентах (экономия трафика), когда нужно агрегировать данные из нескольких источников или когда фронтенд часто меняет структуру запросов. Гибридный подход (REST для простых эндпоинтов + GraphQL для сложных запросов) тоже допустим.

## Q2: Как правильно версионировать API?
Три основных подхода:
- **URL path** (`/v1/users`) — самый явный, легко маршрутизировать, но засоряет URL
- **Header** (`Accept: application/vnd.api+json;version=1`) — чистые URL, но сложнее тестировать
- **Query parameter** (`/users?version=1`) — компромисс, но не идиоматично

Рекомендация: URL path для публичных API, header-based для внутренних. Никогда не ломать обратную совместимость без смены версии.

## Q3: Какой формат ошибок использовать в REST API?
Стандарт RFC 7807 (Problem Details for HTTP APIs):
```json
{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation Error",
  "status": 422,
  "detail": "Field 'email' must be a valid email address",
  "instance": "/users/123",
  "errors": [
    {"field": "email", "message": "Invalid email format"}
  ]
}
```
Всегда возвращайте машиночитаемый `type`, человекочитаемый `detail` и корректный HTTP-статус.

## Q4: Как проектировать пагинацию?
- **Offset-based** (`?offset=20&limit=10`) — простая, но медленная на больших датасетах и нестабильная при вставках
- **Cursor-based** (`?after=eyJpZCI6MTAwfQ&limit=10`) — стабильная, быстрая, но нельзя прыгнуть на произвольную страницу
- **Keyset** (`?created_after=2024-01-01&limit=10`) — хорошая производительность, но только для сортируемых полей

Для публичных API рекомендуется cursor-based пагинация с метаданными `hasNextPage`, `endCursor`.

## Q5: Нужно ли использовать HATEOAS в REST API?
HATEOAS (Hypermedia as the Engine of Application State) — уровень 3 модели зрелости Ричардсона. На практике полный HATEOAS редко реализуют. Разумный компромисс — включать ссылки на связанные ресурсы (`_links`) и действия, но не требовать от клиентов навигации исключительно через гипермедиа. Для внутренних API это обычно избыточно.
