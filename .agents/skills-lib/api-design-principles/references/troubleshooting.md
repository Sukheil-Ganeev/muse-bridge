# Troubleshooting — api-design-principles

## Проблема 1: N+1 запросов в GraphQL
**Симптом:** Один GraphQL-запрос порождает десятки/сотни SQL-запросов к БД, время ответа растёт экспоненциально.
**Решение:** Использовать DataLoader (batching + caching) для всех резолверов, которые обращаются к БД. Паттерн: собрать все ID за один tick event loop, выполнить один batch-запрос.

## Проблема 2: Клиенты получают лишние данные (over-fetching)
**Симптом:** REST-эндпоинт возвращает 50+ полей, клиент использует 5 из них. Высокий расход трафика.
**Решение:** Реализовать sparse fieldsets (`?fields=id,name,email`), создать отдельные lightweight-эндпоинты для списков (`GET /users` — краткая версия, `GET /users/:id` — полная), или мигрировать на GraphQL для критичных сценариев.

## Проблема 3: Breaking changes ломают клиентов
**Симптом:** После деплоя клиенты массово получают ошибки — поле переименовано, тип изменён, эндпоинт удалён.
**Решение:** Следовать принципу аддитивных изменений: добавлять новые поля, не удалять старые. Для удаления — deprecation period (минимум 6 месяцев для публичных API). Использовать sunset-header: `Sunset: Sat, 01 Jan 2025 00:00:00 GMT`. Внедрить contract testing (Pact, Dredd).

## Проблема 4: Неконсистентные HTTP-статусы
**Симптом:** Один эндпоинт возвращает 200 с `{"error": true}`, другой — 400, третий — 500 на одинаковый тип ошибки.
**Решение:** Составить и задокументировать таблицу статусов для проекта:
- `200` — успех
- `201` — ресурс создан
- `204` — успех без тела
- `400` — ошибка валидации
- `401` — не аутентифицирован
- `403` — нет прав
- `404` — ресурс не найден
- `409` — конфликт состояния
- `422` — семантическая ошибка
- `429` — rate limit
- `500` — серверная ошибка

## Проблема 5: Rate limiting не работает корректно
**Симптом:** Легитимные клиенты получают 429, а злоупотребители проходят.
**Решение:** Реализовать многоуровневый rate limiting: по IP (базовый), по API-ключу (основной), по пользователю (точный). Возвращать заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. Использовать sliding window (не fixed window) для равномерности. Для критичных эндпоинтов — отдельные лимиты.

## Проблема 6: GraphQL-запросы слишком глубокие/дорогие
**Симптом:** Клиент отправляет запрос с 10 уровнями вложенности, сервер падает от нагрузки.
**Решение:** Ограничить глубину запросов (`depthLimit(10)`), вычислять стоимость запросов (query cost analysis), установить таймаут на выполнение, ограничить максимальный размер запроса в байтах. Использовать persisted queries для production.
